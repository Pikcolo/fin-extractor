## 5E: Validation (cross-check)

โค้ด: `src/fin_extractor/validation/checks.py`, `tax_id.py`

ตรวจว่าตัวเลขสอดคล้องกันเอง จึงจับ OCR อ่านผิดได้โดยไม่ต้องมีคำตอบที่ถูกมาเทียบ

### หลักการ

เอกสารการเงินมีความสัมพันธ์ของตัวเลขอยู่ในตัว ถ้า OCR อ่านผิดไปหลักเดียว ผลรวมจะไม่ลงตัว
ตอนใช้งานจริงไม่มีคำตอบที่ถูกให้เทียบ แต่ตัวเลขในเอกสารเองเป็นพยานให้กันได้

check ใช้ทำสามอย่าง
1. บอกคนตรวจว่าข้อไหนน่าสงสัยและเพราะอะไร (`detail`)
2. เป็นกรรมการเลือกระหว่างผลจาก rules กับ LLM (5C)
3. เป็นตัวตัดสินสถานะเอกสาร (5F) และเป็นหลักฐานรายฟิลด์ (`review`)

**"ตรวจไม่ได้" ไม่ใช่ "ไม่ผ่าน"** ใบกำกับภาษีอย่างย่อไม่มีชื่อผู้ซื้อ ใบเสร็จบางใบไม่แยกยอดก่อนภาษี ถ้านับว่า
ไม่ผ่าน เอกสารที่ถูกต้องจะตกทุกใบ จึงคืน `null`

| Check | สูตร | ผลกับภาพตัวอย่าง |
|---|---|---|
| `vendor_tax_id_checksum` | หลักที่ 13 = (11 − (Σ d[i] × (13 − i), i = 0..11) mod 11) mod 10 | ✓ 0105559117128 |
| `buyer_tax_id_checksum` | สูตรเดียวกัน (ตรวจเมื่อมีเลขผู้ซื้อ) · checksum ทั้งสองตัวผ่านแล้วไม่นับเป็นตัวยืนยัน (ไม่บอกว่าเลขเป็นของฝ่ายไหน) ไม่ผ่าน = ขัดแย้ง | — |
| `items_sum` | ผลรวมรายการ = ยอดใดยอดหนึ่ง: subtotal / ยอดก่อน VAT / ยอดรวม (ราคารายการรวม VAT) / ยอดรวม − VAT (เมื่อไม่มียอดก่อน VAT) · ไม่ผ่าน: ชี้รายการ + ยอดที่ check อื่นยังไม่ยืนยัน | ✓ 47.98 |
| `discount` | subtotal − discount = ยอดก่อน VAT **หรือ** = ยอดรวม | ✓ 47.98 − 0.42 = 47.56 |
| `before_vat_plus_vat` | ยอดก่อน VAT + VAT = ยอดรวม (ไม่มียอดก่อน VAT ใช้ subtotal − ส่วนลด ยกเว้นเท่ากับยอดรวม = ราคารวม VAT แล้ว ไม่ตรวจ) | ✓ 44.45 + 3.11 = 47.56 |
| `vat_rate` | VAT = ยอดก่อน VAT × อัตรา (ถ้าไม่มี ใช้ ยอดรวม × r / (1 + r)) | ✓ 3.11 |
| `date_range` | 2000-01-01 ≤ วันที่ ≤ วันนี้ (ตรวจแค่ความสมเหตุสมผล ไม่นับเป็นตัวยืนยันว่าอ่านถูกวัน) | ✓ 2023-05-18 |
| `amount_in_words` | จำนวนเงินตัวอักษร แปลงเป็นตัวเลข (`validation/thai_amount.py` ตามหลักการอ่านตัวเลขไทย) = ช่องเงินคู่กัน คู่กำหนดใน config ด้วย `words_of` ของฟิลด์: 50 ทวิ `total_tax_withheld_text` ↔ `total_tax_withheld` · ใบสำคัญรับเงิน `amount_in_words` ↔ `total_amount` อ่านตัวอักษรไม่ได้ (OCR เพี้ยน) = ตรวจไม่ได้ ไม่ใช่ไม่ผ่าน | ✓ 1307 "(หกสิบบาทถ้วน)" = 60.00 |
| `income_rows_sum` | 50 ทวิ: แถว "รวมเงินที่จ่ายและภาษีที่หักนำส่ง" = ผลรวมแถวรายการ ตามนิยามของแบบฟอร์ม แถวรายการ = บรรทัดที่มีวันที่จ่ายและยอดเงินพอดีสองยอด (จ่าย · ภาษีที่หัก) แถวซ้ำตรงตัวนับครั้งเดียว ต้องใช้บรรทัดข้อความ จึงอยู่ใน `pipeline.assess` | ✓ 1307 1321 1323 · 1311 แถวรวมหาย = ตรวจไม่ได้ (detail บอกยอดของแถวรายการ) |
| `reader_complete` | ตัวอ่านตอบจบ ไม่ถูกตัดเพราะชนเพดาน token (pipeline เพิ่มให้เมื่อตอบไม่จบเท่านั้น จึงมีแต่ `passed=false` ผลก่อน 2026-11-20 ชื่อ `vlm_complete`) | — |

`discount` ยอมรับได้สองแบบ เพราะเอกสารไทยมีทั้งราคาแบบไม่รวม VAT (หักส่วนลดก่อนคิดภาษี) และแบบรวม VAT แล้ว (เช่นใบเสร็จตัวอย่าง)

**check บางข้อไม่ปรากฏในผล** เมื่อข้อมูลไม่เข้าเงื่อนไข: `buyer_tax_id_checksum` มีเมื่อมีเลขผู้ซื้อ, `discount` มีเมื่อมีทั้ง subtotal และ discount, `vat_rate` มีเมื่อมี `vat_amount`

**ชนิดเอกสารเลือก check ได้** (`document_types.<ชนิด>.checks` ใน config) ข้อที่ชนิดนั้นไม่ใช้ยังอยู่ในผลแต่เป็น `passed=null` และ `detail` = "ไม่ใช้กับเอกสารชนิดนี้" เช่น 50 ทวิใช้เลขภาษี `date_range` `amount_in_words` `income_rows_sum`

**ค่าที่ยอมให้คลาด:** ±0.02 บาทจากการปัดเศษ (`validation.amount_tolerance`)
**อัตรา VAT ตั้งต้น:** 0.07 เมื่อเอกสารไม่ระบุ (`validation.default_vat_rate`)

แต่ละ check มี 3 ผลลัพธ์:
- `true` ผ่าน
- `false` ไม่ผ่าน
- `null` ข้อมูลไม่พอให้ตรวจ ไม่นับเป็นข้อผิด

**ตัวอย่างที่จับได้จริง:** Tesseract (engine รุ่นก่อน ปัจจุบันถูกลบออกแล้ว) อ่าน 8.05 เป็น 805 ทำให้ผลรวมรายการไม่ตรงกับ 47.98 → `items_sum ✗`

## 5F: สถานะเอกสาร

โค้ด: `src/fin_extractor/validation/scoring.py`

**หลักการ:** ทุกค่าที่รายงานต้องได้มาจากผลของการ process จริง ไม่มีน้ำหนักหรือเกณฑ์ตัวเลขที่ตั้งขึ้นเอง
รุ่นก่อนรวมเป็นคะแนนเดียวด้วยน้ำหนัก 0.3 / 0.5 / 0.2 และเกณฑ์ 0.85 แต่ตัวเลขเหล่านี้ไม่มีงานวิจัยหรือข้อมูลรองรับ จึงตัดออก

ค่าที่รายงาน (วัดได้ทั้งหมด):

| ค่า | ที่มา |
|---|---|
| ฟิลด์ที่ขาด (`review` ระดับ `missing`) | field ที่ชนิดเอกสารต้องมีแต่หาไม่เจอ ค่าตั้งต้น (generic) คือ `vendor.name`, `vendor.tax_id`, `invoice_no`, `date`, `total_amount` โปรไฟล์ชนิดเอกสารกำหนด `required` เองได้ และตัดช่องที่ชนิดนั้นไม่มี (`not_applicable`) ออก |
| `checks` | ผล check แต่ละข้อจาก 5E |
| `ocr_confidence` | ค่าเฉลี่ยที่ OCR engine รายงานเอง (มีเฉพาะ Paddle / OpenThai Text ตัวอื่นไม่มีคีย์) — รายงานไว้ดู ไม่ได้ใช้ตัดสินสถานะ เพราะยังไม่มีข้อมูลบอกว่าค่าเท่าไรถึงเชื่อได้ |

สถานะตัดสินด้วยกฎ เป็น**ลำดับความเร่งในการตรวจ** เจ้าหน้าที่ตรวจทุกใบอยู่แล้ว ไม่มีสถานะไหนข้ามการตรวจ (ชื่อเดิมก่อน 2026-11-26: `auto_approved` → `ready` · `needs_review` → `check` · `failed` → `incomplete` · เลิกใช้ `status: draft` ของโปรไฟล์):

| สถานะ | เงื่อนไข | ความหมาย |
|---|---|---|
| `incomplete` | หายอดหลัก (`primary_amount` ของโปรไฟล์ ค่าตั้งต้น `total_amount`) ไม่เจอ | ต้องกรอกยอดหลักเอง |
| `ready` | ไม่มีฟิลด์ที่ขาด **และ** ไม่มี check ไหนไม่ผ่าน **และ** มี check ที่ยืนยันค่าผ่านอย่างน้อยหนึ่งข้อ (ไม่นับ `date_range` และ checksum เลขภาษี ซึ่งบอกแค่ว่ารูปแบบใช้ได้) | ดูเทียบภาพผ่าน ๆ (ชื่อ เลขที่ วันที่ เลขภาษี ยังไม่มีตัวยืนยัน ต้องดู) |
| `check` | กรณีอื่น | ดูช่องที่ไฮไลต์ (ขัดแย้ง / หาไม่เจอ) |

**ตัวอย่าง:** `BITKUB-001.jpg` ผ่าน check 6/6 แต่ช่องเลขที่เอกสารในใบว่าง → `review.invoice_no.level = "missing"` → `check`

**ข้อควรระวัง: `ready` ไม่ได้แปลว่าค่าถูก แปลว่าตัวเลข "สอดคล้องกันเอง"** (พบจากการรันโหมด `--mode vlm` รุ่นเก่าที่อ่านทั้งหน้า (ลบแล้ว) กับสแกนจริง 18 ใบ)
ใบ 001307 (หนังสือรับรองหัก ณ ที่จ่าย) ได้ `ready` ทั้งที่ข้อความดิบมีตัวเลขเงิน (ทศนิยม 2 ตำแหน่ง) แค่ `2,000.00` และ `60.00` (ภาษีที่หัก)
LLM สกัดเป็น VAT `120.0` อัตรา 6% และยอดรวม `2120.0` ซึ่ง **ไม่พบในข้อความดิบ** (ตรวจเฉพาะรูปแบบทศนิยม 2 ตำแหน่ง) แต่ผ่าน check "ก่อน VAT + VAT = รวม" ทุกข้อเพราะตัวเลขที่แต่งขึ้นสอดคล้องกันเอง
check จับได้เฉพาะค่าที่ไม่สอดคล้อง (เช่น เลขภาษีที่ checksum ไม่ผ่าน) จับค่าที่ถูกแต่งให้สอดคล้องไม่ได้
ผู้ใช้ผลจากโหมดที่ใช้ LLM จึงไม่ควรอนุมัติอัตโนมัติโดยไม่ตรวจว่าค่าอยู่ในข้อความดิบจริง ปัจจุบันหลักฐานรายฟิลด์ตรวจว่าค่าอยู่ในข้อความหรือไม่ (ไม่อยู่ = `review` ระดับ `conflict` เหตุผล "ค่านี้ไม่ปรากฏในข้อความที่ OCR อ่านได้") และ `--llm hybrid` ปัดค่าที่ไม่อยู่ในข้อความ แต่ `decide_status` ยังไม่ใช้ `grounded`

**ถ้าอยากได้คะแนนเป็นตัวเลขในอนาคต** ต้องหาน้ำหนักและเกณฑ์จากข้อมูล ไม่ใช่ตั้งเอง: เก็บเอกสารที่มีเฉลย
แล้วดูว่าสัญญาณแต่ละตัว (check, field ที่ขาด, ocr_confidence) ทำนายว่าผลถูกหรือผิดได้ดีแค่ไหน

**ข้อควรรู้:** สถานะเป็นของ **ทั้งเอกสาร** ส่วนว่า **ช่องไหน** ต้องดูอยู่ใน `review` (ระดับ + เหตุผลรายฟิลด์ เรียงตามที่ควรตรวจก่อน)
ถ้าต้องการคะแนนรายฟิลด์เป็นตัวเลข ต้องมีสัญญาณมากกว่านี้ (โปรเจกต์รุ่นก่อนใช้ 6 สัญญาณต่อฟิลด์:
ความมั่นใจของโมเดล, หาค่าเจอในข้อความจริงไหม, รูปแบบถูกไหม, ยอดเงินลงตัวไหม, ผู้ขายอยู่ในทะเบียนไหม,
ถามซ้ำได้คำตอบเดิมไหม)

## 5G: บันทึกผล

โค้ด: `src/fin_extractor/cli.py → cmd_extract`

บันทึกเป็น `data/05_extract/<dataset>/<engine>/<วิธี>/<rules|llm|hybrid>/<ชื่อไฟล์>_p<หน้า>.json` (วิธี = `regions-luma` ค่าตั้งต้น หรือ `luma|flat|bin|color` ของผัง section แบบเดิม ข้อความดิบแยกไว้ที่ `data/04_ocr/<dataset>/<engine>/<วิธี>/` พร้อม `manifest.json` ของรัน) ตามโครง `ExtractionResult` (JSON Schema เต็มอยู่ที่ `schemas/invoice.schema.json`)

### หลักการของ schema (Data Contract)

schema คือ **ข้อตกลง** ว่าผลลัพธ์หน้าตาแบบไหน ไม่ว่าจะมาจาก Paddle + rules หรือ Typhoon/OpenThai + LLM ก็คืน
`ExtractionResult` รูปเดียวกัน ระบบบัญชีปลายทางใช้ต่อได้โดยไม่ต้องรู้ว่าข้างในทำงานยังไง และเปลี่ยน
engine ได้โดยไม่ทำให้ฝั่งนั้นพัง

เขียนด้วย **Pydantic** (`src/fin_extractor/schema.py`) ได้ประโยชน์สามต่อ
1. **ตรวจชนิดข้อมูลอัตโนมัติ** เช่น `tax_id` ต้องเป็นตัวเลข 13 หลัก (`^\d{13}$`)
2. **export เป็น JSON Schema ได้** (`python -m fin_extractor schema`) ส่งให้ทีมระบบบัญชีดูเป็นสเปกได้
3. **เป็นเอกสารในตัว** ทุกฟิลด์มี description

```
ExtractionResult                     ผลของ 1 หน้า
├── schema_version                   "4.0"
├── source_file, page, engine
├── data: InvoiceData                ข้อมูลที่ระบบบัญชีใช้ (ค่าอยู่ที่นี่ที่เดียว)
│   ├── vendor / buyer: Party
│   ├── items: [LineItem]
│   └── ยอดเงิน, วันที่, เลขที่เอกสาร, เล่มที่
├── checks: [ValidationCheck]        ผลการตรวจแต่ละข้อ + ฟิลด์ที่ใช้ตรวจ (fields)
├── review: {คีย์: FieldReview}      ต่อฟิลด์: level + reasons (+ source ถ้าไม่ใช่ rules) เรียงตามที่ควรตรวจก่อน
├── status
├── ocr_confidence                   (มีเฉพาะเมื่อตัวอ่านรายงาน: Paddle / OpenThai Text)
├── raw_text                         (เฉพาะเมื่อใส่ --keep-raw) ข้อความดิบไว้ debug
└── rejected: [RejectedValue]        (เฉพาะเมื่อมี: --llm hybrid) ค่าที่ LLM เสนอแต่ไม่ถูกรับ: key, reason
```

หลักที่ใช้ออกแบบ
- **แยกข้อมูลธุรกิจ (`data`) ออกจากผลการตรวจ (`checks`, `status`)** ฝั่งบัญชีหยิบ `data` ไปใช้ได้ตรง ๆ
- **วันที่เป็น ISO ค.ศ. เสมอ** ระบบปลายทางไม่ต้องแปลง พ.ศ. เอง
- **`extra="ignore"`** ถ้า LLM ตอบฟิลด์เกินมา ตัดทิ้งเงียบ ๆ แทนที่จะล้ม
- **ทุกฟิลด์ว่างได้** (`None`) เพื่อให้ตอบว่า "ไม่เจอ" ได้ แทนการเดาค่า

**ยอดเงินเป็น `Decimal`** (schema 2.0) JSON ส่งเป็นสตริง เช่น `"47.56"` เพื่อไม่ให้ปัดเศษเพี้ยนแบบ `float`
ยอดเงิน 5 ช่องของ `data` และ `items[].amount` ถูกปัดเป็น 2 ตำแหน่ง (ROUND_HALF_UP) ส่วน `vat_rate`, `quantity`, `unit_price`
เป็น Decimal ที่ไม่ปัด ระบบปลายทางที่เคยอ่านเป็นตัวเลข (schema 1.x) ต้องแปลงสตริงเอง ค่าคลาดของ check ยังเป็น ±0.02 บาทตาม config

**`review`** คีย์เป็นชื่อฟิลด์แบบ `vendor.tax_id`, `total_amount`, `items[0].amount`, `document_fields.<key>` เรียง conflict → missing → unverified → verified → not_applicable
ค่าเป็น `level` + `reasons` (คำพูด เช่น "check items_sum ไม่ผ่าน (…)", "ค่านี้ไม่ปรากฏในข้อความที่ OCR อ่านได้", "ยืนยันแล้วด้วย before_vat_plus_vat") และ `source` เมื่อค่ามาจาก `llm`, `human` หรือตัวอ่านเสริมของชั้นตรวจความครบ (ชื่อตัวอ่าน เช่น `openthai-text`)
ฟิลด์ที่ไม่มีค่าและไม่บังคับไม่อยู่ใน `review` สร้างจากหลักฐานละเอียด (`FieldEvidence`: checksum, check ที่ผ่าน/ไม่ผ่าน, อยู่ในข้อความไหม, สองแหล่งตรงกันไหม) ซึ่งใช้ภายใน (`validation/evidence.py → review_from_evidence`) กฎอยู่ใน [06 หัวข้อ 4.3](06-design-and-roadmap.md)

```json
"review": {
  "invoice_no":    {"level": "missing", "reasons": ["เอกสารชนิดนี้ต้องมี แต่ระบบหาไม่เจอ ให้กรอกจากภาพ"]},
  "vendor.name":   {"level": "unverified", "reasons": ["ไม่มี check ที่ยืนยันค่านี้ได้ ให้ดูเทียบกับภาพ"]},

```

**schema 4.0 (2026-11-24)** เทียบ 3.0: `field_evidence` (10 ช่องต่อฟิลด์ ส่วนใหญ่ว่างเสมอ และเก็บค่าซ้ำกับ `data`) → `review` · ตัด `missing_fields` (= `review` ระดับ `missing` ใน Python ยังเรียก `result.missing_fields` ได้) และ `handwritten_fields` (ว่างเสมอ) · `ocr_confidence` `raw_text` `rejected` ไม่ถูกเขียนเมื่อว่าง
บน 18 ใบ (OpenThai luma rules): ค่า สถานะ check และฟิลด์ที่ขาดเหมือน 3.0 ทุกใบ ระดับรายฟิลด์เหมือนทุกใบ JSON รวมเล็กลง 35% (6,010 → 3,879 บรรทัด)
**ไฟล์ 2.x/3.x ไม่ถูกแปลงแล้ว** (ตัวโหลดผลเก่าถูกลบ 2026-11-26) ผลเก่าให้สกัดใหม่ด้วย `extract` (CPU อ่านข้อความดิบเดิม)

### ข้อจำกัดของ check ที่เจอระหว่างทำหน้าตรวจ

แก้แล้ว (2026-11-24): เดิม `items_sum` เทียบกับยอดตัวแรกที่มีเท่านั้น (subtotal → ก่อน VAT → ยอดสุทธิ) ร้านที่พิมพ์ราคารายการรวม VAT แล้วจึงไม่ผ่านแม้รายการถูก และ `before_vat_plus_vat` ไม่ตรวจเมื่อมีแค่ subtotal
ตอนนี้ผ่านถ้าตรงยอดใดยอดหนึ่ง (รวม ยอดรวม − VAT) · subtotal แทนยอดก่อน VAT ได้ · ถ้าไม่ผ่าน ยอดที่ check อื่นยืนยันแล้วไม่ถูกชี้ว่าขัดแย้ง
ผลบน 18 ใบ (OpenThai regions ไม่ OCR ใหม่): 1308 ผ่านทั้งสอง check (subtotal 23,140.19 + VAT 1,619.81 = 24,760.00 = รายการ) สถานะเป็น ready ·
1309 `before_vat_plus_vat` ผ่าน รายการรวม 3,860 ไม่ตรงยอดใด ชี้เฉพาะรายการ · 1318 รายการ 7,500 = 8,025 − 525 ผ่าน

## Ground truth ที่คนกรอก (วัดความถูก ไม่ใช่แค่ความครบ)

ตัวเลขผลวัดก่อนหน้านี้ทั้งหมดนับแค่ "ฟิลด์ที่ขาด" ไม่รู้ว่าค่าที่ได้ถูกหรือผิด ground truth ปิดช่องนี้สำหรับชุดพัฒนา โดยข้อมูลไม่ออกนอกเครื่อง

1. **กรอก:** `python scripts/eval/groundtruth_app.py data/01_input/finance_doc_scan` แล้วเปิด `http://127.0.0.1:8765`
   - ซ้ายคือภาพ final ขวาคือฟอร์มที่เติมค่าจากผลสกัดไว้แล้ว
   - แก้ให้ตรงเอกสาร ช่องที่เอกสารไม่มีให้ติ๊ก "ไม่มี" รายการสินค้ากรอกเป็นตาราง (ติ๊ก "ตรวจรายการแล้ว" จึงนับคะแนน)
   - "บันทึกร่าง" ยังไม่นับคะแนน "ตรวจเสร็จ" นับ
2. **ไฟล์:** `data/etc/groundtruth/<dataset>/<ไฟล์>.json` ค่า `null` = เอกสารไม่มีช่องนี้ (รูปแบบใน `src/fin_extractor/groundtruth.py`)
3. **ให้คะแนน:** `python scripts/eval/score_groundtruth.py data/01_input/finance_doc_scan --by-field`
   - เทียบทุกชุดผลใต้ `05_extract/<dataset>/` เช่น `openthai/luma/rules` กับ `openthai/regions-luma/rules`
   - เทียบหลัง normalize ตามชนิดค่า: เงินเทียบเป็นค่า (`1,940.00` = `1940`), เลขภาษีเทียบตัวเลขล้วน, ข้อความตัดช่องว่างและแก้สระอำ
   - ไม่มีเกณฑ์ความคล้าย ต่างตัวเดียวก็ผิด

ground truth ชุดนี้ใช้ตอนพัฒนาเท่านั้น (เลือกวิธีแบ่งหน้า/engine) ตอนใช้งานจริงไม่มีเฉลย นอกจากค่าที่นักบัญชียืนยันหรือแก้ในหน้าตรวจ ซึ่งเก็บในรูปเดียวกันนี้ได้
