# ขั้นที่ 3: อ่านข้อความ

แยกเป็นสองทางตามโหมด:
- `--mode ocr` → **3A** OCR engine แบบดั้งเดิม
- `--mode vlm` → **3B** Typhoon OCR (Vision Language Model)

## หลักการ

แปลงภาพเป็นข้อความ มีผู้อ่านสองตระกูลที่ทำงานต่างกันโดยสิ้นเชิง

| | OCR แบบดั้งเดิม (3A) | VLM (3B) |
|---|---|---|
| ตัวอย่าง | PaddleOCR (Tesseract และ EasyOCR เคยรองรับ ถูกลบออกแล้ว) | Typhoon OCR 1.5 |
| วิธีอ่าน | หาตัวอักษรทีละคำ | โมเดลภาพอ่านทั้งหน้าในครั้งเดียว |
| ได้อะไร | คำ + **กรอบตำแหน่ง** + **ความมั่นใจต่อคำ** | **Markdown** (ตารางเป็น HTML) |
| จุดแข็ง | เร็ว ไม่ต้องใช้ GPU รู้ตำแหน่งของคำ | เข้าใจตารางและ layout อ่านภาษาไทยแม่นมาก |
| จุดอ่อน | ไทยแม่นน้อยกว่า คอลัมน์ตัวเลขหายง่าย | ช้า ไม่มีตำแหน่ง ไม่มีความมั่นใจต่อคำ |

ทั้งสองทางต้องคืนผลที่ขั้นที่ 4 ใช้ต่อได้ จึงจบที่ **list ของบรรทัดข้อความ** เหมือนกัน

**ภาษาไทยมีเรื่องเฉพาะสองเรื่อง** ที่ต้องแก้หลังอ่านทุกครั้ง
- **ไทยไม่เว้นวรรคระหว่างคำ** แต่ OCR ตัดคำไทยเป็นชิ้นเล็ก ถ้าต่อด้วยช่องว่างตรง ๆ จะได้ `บ ร ิ ษั ท`
  จึงเว้นวรรคเฉพาะเมื่อภาพมีช่องว่างจริง (ข้อ 3 ของ 3A)
- **สระอำถูกเขียนเป็นสองตัว** นิคหิต (U+0E4D) + สระอา (U+0E32) ซึ่งเป็นคนละตัวอักษรกับสระอำ (U+0E33)
  และ `unicodedata.normalize` แก้ให้ไม่ได้ ถ้าไม่แก้ คำว่า "จำกัด" ในชื่อบริษัทแทบทุกชื่อจะเทียบไม่ตรง

### ทำไม Typhoon คืน Markdown ไม่ใช่ JSON

Typhoon OCR เป็น **โมเดล OCR** ไม่ใช่โมเดลที่ตอบตาม schema ได้ ผู้พัฒนาระบุว่าใช้กับ prompt ที่กำหนด
เท่านั้น จึงต้องมีขั้นที่ 4 แปลง Markdown เป็นฟิลด์อีกครั้ง prompt บางแบบในแพ็กเกจที่บอกให้ตอบ JSON
ก็เป็นแค่ซอง `{"natural_text": "<Markdown>"}` ไม่ใช่ฟิลด์ที่สกัดแล้ว (`_strip_wrappers` แกะซองนี้ออก)

โปรเจกต์รุ่นก่อนลองบังคับให้ Typhoon ตอบ JSON ตาม schema เอง ได้ฟิลด์ถูกแค่ 28.6% เทียบกับ 92.9%
เมื่อให้มันอ่านเป็นข้อความแล้วค่อยสกัดด้วยขั้นถัดไป

### ผลเทียบสองตระกูล (โปรเจกต์รุ่นก่อน)

ชุดทดสอบ 2 ใบ ใช้ตัวสกัด regex ตัวเดียวกัน ต่างกันแค่ผู้อ่าน

| | Tesseract | Typhoon OCR |
|---|---|---|
| ฟิลด์ถูก | 71.4% | 92.9% |
| CER ระดับฟิลด์ | 0.273 | 0.002 |
| เวลาต่อใบ | ~10 วินาที | ~19 วินาที |

## 3A: OCR engine

โค้ด: `src/fin_extractor/ocr/`

ใช้ engine ตัวเดียวคือ PaddleOCR เพื่อลดภาระติดตั้งและดูแล ทุก engine ยังคืนค่าในรูปแบบกลาง (`OCRResult` ใน `base.py`)
ถ้าจะเพิ่ม engine อื่นภายหลัง ไม่ต้องแก้ขั้นถัดไป

| Engine | ไฟล์ | จุดเด่น | ตั้งค่า (`ocr.*`) |
|---|---|---|---|
| PaddleOCR | `paddle_engine.py` | แม่นยำสูงในผลเทียบด้านล่าง รองรับทั้ง API v2 และ v3 | `lang: th`, `use_angle_cls: false` |

Tesseract (`tha+eng`) และ EasyOCR (`th, en`) เคยรองรับ ถูกลบออกแล้ว ผลเทียบตอนยังมีอยู่ในหัวข้อ "ผลเทียบสาม engine" ด้านล่าง

### ขั้นย่อย

1. **รัน engine** ได้คำแต่ละคำ พร้อมข้อความ, ความมั่นใจ (0–1) และกรอบ (x0, y0, x1, y1)
2. **จัดกลุ่มเป็นบรรทัด**
   - Paddle คืนกล่องคำลอย ๆ จึงใช้ `group_into_lines`: คำที่ความสูงซ้อนกัน ≥ 50% อยู่บรรทัดเดียวกัน แล้วเรียงซ้ายไปขวา
3. **ต่อคำในบรรทัด** (`OCRLine.text`) โดยเว้นวรรคเฉพาะเมื่อในภาพมีช่องว่างจริง
   - ไทยกับไทย: เว้นวรรคเมื่อช่องว่างกว้างกว่า 50% ของความสูงตัวอักษร
   - อังกฤษหรือตัวเลข: เว้นวรรคเมื่อช่องว่างกว้างกว่า 10%
   - ถ้าไม่ทำขั้นนี้ engine ที่ตัดเป็นคำหรือตัวอักษรย่อย ๆ (เช่น Tesseract) จะได้ `บ ร ิ ษั ท` แทน `บริษัท`
4. **แก้ตัวอักษรไทย** (`normalize_thai`): เปลี่ยน `ํา` (นิคหิต + สระอา) เป็น `ำ`

### ผลลัพธ์
- list บรรทัดข้อความ
- ข้อความดิบทั้งหน้า (`raw_text`)
- ความมั่นใจเฉลี่ย (`ocr_confidence`) ใช้ในขั้นคิดคะแนน

### ผลเทียบสาม engine บนเครื่องนี้

> วัดตอนที่ยังรองรับสาม engine และใช้ preprocessing แบบเก่า (สอง profile) ปัจจุบันเหลือ Paddle ตัวเดียวกับ preprocessing ชุดเดียว
> เวลาเตรียมภาพในตารางจึงสูงกว่าปัจจุบัน (NL-means ที่ใช้ตอนนั้นปิดแล้ว ดู [02-preprocessing.md](02-preprocessing.md))

รันไปป์ไลน์เต็ม `--mode ocr` (RTX 4050 6 GB, CUDA 13) เวลาวัดหลังอุ่นเครื่องแล้ว

| | Tesseract | EasyOCR (GPU) | **PaddleOCR (GPU)** |
|---|---|---|---|
| BITKUB-001 อ่านค่าสำคัญเจอ | 6/6 | 5/6 | **6/6** |
| BITKUB-001 สถานะ | needs_review 0.84 | auto_approved 0.89 | **auto_approved 0.93** |
| BITKUB-001 รายการสินค้า | 2/5 (อ่าน `8.05` เป็น `805`) | 5/5 | **5/5** |
| BITKUB-001 ชื่อผู้ขาย | ไม่มีเว้นวรรค | ขาดการันต์ (`ออนไลน`) | **ถูกทุกตัว** |
| VATGB-001 อ่านค่าสำคัญเจอ | 3/5 | 3/5 | **5/5** |
| เวลา BITKUB / VATGB | **4.5 / 3.7 วิ** | 7.3 / 12.6 วิ | 5.1 / 23.3 วิ |

- **PaddleOCR แม่นที่สุด** โมเดลภาษาไทย `th_PP-OCRv5_mobile_rec` (`lang: th`) อ่านภาษาไทยได้สะอาด
  ตัว OCR เองใช้แค่ราว 0.5 วินาทีบน BITKUB เวลาที่เหลือเป็นขั้นเตรียมภาพ — บน VATGB (2481×3508 px)
  NL-means ใช้ 5.2 วินาที OSD 3.0 วินาที (ทั้งสองขั้นเปลี่ยนแล้ว)
- **EasyOCR ได้ `auto_approved` ทั้งที่ชื่อผู้ขายผิด** (ขาดการันต์) และไม่ได้ยอดก่อนภาษี — กฎตรวจตัวเลข
  ตรวจชื่อไม่ได้ คะแนนจึงผ่าน
- **VATGB ได้ `failed` ทุก engine** ทั้งที่ Paddle อ่านยอดรวม `£20,017.57` ออกมาได้ — ปัญหาอยู่ที่ขั้นที่ 4
  (rules จับบรรทัด `TOTAL` เป็น `subtotal`) ไม่ใช่ OCR
- **ต้องปิด `use_angle_cls` ของ Paddle** ตัวจำแนกทิศรายบรรทัดตัดสินผิดว่าบรรทัดไทยกลับหัวแล้วหมุนกลับ
  อ่านได้ `81-SO-EZOZ` แทน `2023-05-18` (3 จาก 28 บรรทัด) ทิศของทั้งหน้าตรวจแล้วในขั้นที่ 2

## 3B: Typhoon OCR (VLM)

โค้ด: `src/fin_extractor/vlm/`

VLM อ่านทั้งหน้าเป็น Markdown และเข้าใจ layout/ตารางได้ดีกว่า OCR แบบดั้งเดิมมาก แต่ไม่มีกรอบตำแหน่งและไม่มีความมั่นใจต่อคำ

### ขั้นย่อย

1. **ย่อภาพ** ให้ด้านยาวไม่เกิน 1800 px (`vlm.max_image_side`) เพราะ VLM คิด token ตามขนาดภาพ
2. **Encode** เป็น base64 PNG
3. **ส่ง prompt** (`prompts.py → TYPHOON_OCR_PROMPT`) สั่งให้คืน Markdown, ตารางเป็น `<table>` HTML, ห้ามมีคำอธิบายเพิ่ม
4. **เรียกโมเดล** ผ่าน `client.py` ซึ่งรองรับ 2 provider:

   | provider | endpoint | ใช้กับ |
   |---|---|---|
   | `ollama` (ค่าตั้งต้น) | `http://localhost:11434/api/chat` | Ollama ในเครื่อง ตั้ง `num_ctx` ได้ |
   | `openai` | OpenAI-compatible `/v1` | Typhoon API บน cloud, vLLM |

   ต้องใช้ native API ของ Ollama เพราะ endpoint แบบ OpenAI ตั้ง `num_ctx` ไม่ได้
   ค่าตั้งต้น 4096 token ไม่พอ ภาพ 1 หน้ากินไปราว 3.5k token แล้ว ทำให้ VLM ตอบไม่จบ จึงตั้งไว้ที่ 16384

5. **ทำความสะอาดผลลัพธ์** (`_strip_wrappers`): ลบ ```` ```markdown ```` หรือ `{"natural_text": ...}` ที่บางรุ่นห่อมา
6. **ตรวจว่าตอบจบไหม:** ถ้า `finish_reason = length` ระบบเพิ่ม check `vlm_complete ✗` เตือนว่าข้อมูลอาจขาด
7. **แปลงเป็นบรรทัด** (`markdown_to_lines`): ตาราง 1 แถว = 1 บรรทัด คั่นช่องด้วย ` | ` ลบ tag และตัวหนา เพื่อให้ rules ในขั้นที่ 4 ใช้ต่อได้

### ผลลัพธ์
- Markdown ทั้งหน้า (`raw_text`) ใช้ส่งให้ LLM
- list บรรทัด ใช้ส่งให้ rules
- ไม่มี `ocr_confidence`

## เปรียบเทียบกับภาพตัวอย่าง

| | Tesseract | Typhoon OCR |
|---|---|---|
| ยอดรายการ | อ่าน `8.05` เป็น `805`, `5.29` เป็น `529` | ถูกทั้ง 5 รายการ |
| ยอดสรุป | ถูกครบ (หลังลบเส้นตาราง) | ถูกครบ |
| โครงตาราง | ไม่มี (เป็นบรรทัดข้อความ) | ได้ `<table>` ครบทุกแถว |
| เวลา | ~4.5 วินาที | ~50 วินาที |

ดูข้อความดิบด้วย `python -m fin_extractor ocr <ไฟล์> --engine paddle|vlm` (บันทึกที่ `data/output/ocr/<อินพุต>__<engine>/text/` ผล Paddle เป็น `.txt`, ผล VLM เป็น `.md`)

## ผลบนลายมือ: Typhoon OCR ทั้งหน้า เทียบ PaddleOCR (สแกนจริง 4 ใบ)

ทดสอบกับใบที่ Paddle พลาดหนักในชุด `finance_doc_scan`: ใบสำคัญรับเงินลายมือ (001320, 001322) และหนังสือรับรองหัก ณ ที่จ่ายที่ช่องเลขเขียนด้วยมือ (001307, 001323)
ไม่มีเฉลย จึงดูเลข 13 หลักที่ผ่าน checksum และอ่านเทียบกับภาพด้วยตา ผลข้อความอยู่ที่ `data/output/ocr/finance_doc_scan__vlm/text/*_p1.md` (ถ้ารัน `ocr --engine vlm`)

| ใบ | เลขภาษีที่ checksum ผ่าน: Paddle | เลขภาษีที่ checksum ผ่าน: VLM ทั้งหน้า | เวลา VLM |
|---|---|---|---|
| 001320 | ไม่มี | ไม่มี (อ่านได้ 13 หลักแต่ผิดหนึ่งหลัก `[เลขลายมือ ปกปิด]`) | 143.9 s |
| 001322 | ไม่มี | ไม่มี (อ่านได้ `[เลขลายมือ ปกปิด]` ผิดรูป) | 28.0 s |
| 001307 | ไม่มี | `[เลขผู้ซื้อ ปกปิด]` | 49.9 s |
| 001323 | ไม่มี | `[เลขผู้ซื้อ ปกปิด]`, `[เลขลายมือ ปกปิด]` | 56.5 s |

- **ลายมือทั่วไป VLM อ่านได้ดีกว่ามาก:** 001320 และ 001322 ได้ชื่อ ที่อยู่ วันที่ และตารางพร้อมยอด `103,062 50` ครบ ขณะที่ Paddle ได้ข้อความเพี้ยน (เช่น เลขภาษีเหลือ `[เลขลายมือ ปกปิด]`)
- **เลขภาษีลายมือยังพลาด** 2 จาก 2 ใบ ซึ่งการตรวจ checksum จับได้ ไม่ปล่อยค่าผิดผ่านไปเงียบๆ
- **ข้อจำกัด:** ตัวอย่างน้อย (4 ใบ) ไม่มีเฉลย และเวลา 143.9 วินาทีของใบแรกรวมการโหลดโมเดล
## ผลเทียบสองโหมดบนสแกนจริง 18 ใบ (`--mode ocr` เทียบ `--mode vlm`)

> **หมายเหตุ (2026-11-11):** ตัวเลขและข้อสังเกตในหัวข้อนี้มาจากรันของ 2026-11-10 ก่อนมีโปรไฟล์ชนิดเอกสาร ผลดิบชุดนั้น (รวม `ocr-llm`) ถูกลบแล้ว
> รันใหม่ได้ ocr-rules 15 `needs_review`/3 `failed`, vlm-llm 16 `needs_review`/2 `auto_approved` (ดู [README](README.md)) ข้อสังเกตเรื่องค่าผิดของ LLM ด้านล่างยังไม่ได้ตรวจซ้ำกับรอบใหม่
> ตาราง `data/output/benchmarks/compare_modes.md` เป็นของรอบเก่า

เก็บผลสองชุดคู่กัน ชุด A `data/output/extract/finance_doc_scan__ocr-rules/` = `--mode ocr` (Paddle + rules) ชุด B `data/output/extract/finance_doc_scan__vlm-llm/` = `--mode vlm --keep-raw`
(Typhoon OCR + `qwen2.5:3b` + rules) ตารางเทียบรายใบ: `data/output/benchmarks/compare_modes.md` (สร้างด้วย `scripts/compare_modes.py`) ไม่มีเฉลย

| | A: ocr | B: vlm |
|---|---|---|
| `failed` | 7 | **0** |
| `needs_review` | 11 | 17 |
| `auto_approved` | 0 | 1 (001307 แต่ผิด ดูข้างล่าง) |
| ใบที่ขาด field สำคัญ | 15 ใบ | 6 ใบ (ทุกใบขาด `invoice_no`) |
| ผู้ชนะระหว่าง rules กับ LLM | — | LLM 17 ใบ, rules 1 ใบ |
| เวลา/ใบ | 2–5 วินาที (ไม่รวมสองใบแรกที่โหลดโมเดล) | 32–65 วินาที ยกเว้น 001323 ใช้ **611.7 วินาที** (ไม่ทราบสาเหตุ) |

VLM ได้ field ครบกว่าและผ่าน check มากกว่า แต่ **ตัวเลข `failed` 0 ไม่ได้แปลว่าถูก** ผมตรวจค่าที่น่าสงสัยเทียบกับข้อความดิบ (`raw_text`) และ checksum พบ

| ปัญหา | ใบ | รายละเอียด |
|---|---|---|
| **LLM แต่งค่าที่ไม่มีในข้อความ** | 001321, 001314, 001307 | เลขภาษี `0123456789012`/`0123456789013` (001321) และ `3274871214824` (001314) ไม่อยู่ในข้อความดิบเลย checksum จับได้ ส่วน 001307 ข้อความดิบมีตัวเลขเงิน (ทศนิยม 2 ตำแหน่ง) เพียง `2,000.00` กับ `60.00` แต่ LLM ได้ VAT 120 อัตรา 6% และยอดรวม 2120 จน `auto_approved` (ผมตรวจเฉพาะรูปแบบทศนิยม 2 ตำแหน่ง ไม่ได้อ่านภาพทั้งใบ) |
| **ปีผิด** | 001306, 001317, 001311 | ข้อความดิบเป็น `05/10/2569`, `15/10/2569` (= 2026) แต่ LLM ได้ `2022-10-05`, `2022-10-15` และ 001311 ได้ `2020-10-08` ขณะที่ rules ได้ปี 2026 |
| **สลับผู้ขาย/ผู้ซื้อ** | 001310 | `vendor.tax_id` ได้เลขของผู้ซื้อ (`[เลขผู้ซื้อ ปกปิด]`) ทั้งที่ผู้ขายคือ `[เลขผู้ขาย ปกปิด]` ซึ่งโหมด ocr ได้ถูก |
| **เลขลายมืออ่านผิดหลักเดียว** | 001320, 001322 | `[เลขลายมือ ปกปิด]`, `[เลขลายมือ ปกปิด]` ไม่ผ่าน checksum (แต่ถูกจับได้) |

ข้อสรุปที่พูดได้อย่างระมัดระวัง
- VLM ช่วย **การอ่านข้อความ** (ลายมือ ชื่อ ตาราง) ได้จริง แต่ชั้น **LLM สกัด** แต่งค่าและแปลงปีผิดได้ ผลจึงต้องตรวจทาน ไม่ควรอนุมัติอัตโนมัติ
- ยังไม่มีเฉลย จึงไม่รู้ว่าฝั่งไหนถูกทั้งหมดกี่ค่า ที่ตรวจไปคือค่าที่ขัดกับข้อความดิบหรือ checksum เท่านั้น
- เอกสารที่ไม่ใช่ใบกำกับภาษี (50 ทวิ ใบสำคัญรับเงิน ใบเสร็จศุลกากร) ไม่เข้ากับ schema (ผู้ขาย/ผู้ซื้อ, ยอดก่อน VAT) บทบาทของ `vendor`/`buyer` ใน 50 ทวิจึงกำกวม
- ทางที่น่าลอง (ยังไม่ได้ทำ): ใช้ VLM เป็นตัวอ่าน แต่สกัดด้วย rules หรือตรวจว่าทุกค่าอยู่ในข้อความดิบ แล้วค่อยให้ LLM เติมเฉพาะที่ขาด
