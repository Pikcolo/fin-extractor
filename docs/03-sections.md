# ขั้นที่ 3: แบ่งหน้าเป็น section ก่อน OCR (flow หลัก)

> **สถานะ:** ใช้กับสแกน `finance_doc_scan` ครบ 18 ใบ (OpenThai, ภาพ luma, ผัง `rows`) ต่อเข้า `extract` แล้ว (ขั้น 5) ทุก engine อ่านทีละ section (ห้ามอ่านทั้งหน้า)
> **ไม่มีเฉลย** ตารางผลวัดทั้งหมดในหน้านี้วัดจาก **9 ใบ** (1306 1307 1308 1310 1312 1313 1316 1317 1320) ด้วย "ฟิลด์ที่ rules สกัดไม่เจอ" และคู่ป้าย–ค่า ไม่ได้วัดว่าค่าที่เจอถูกหรือไม่
> ยอดรวมของ 4 ใบที่เคยตก `failed` ตอนส่งทั้งแผ่น (1307, 1309, 1321, 1323) ตรงกับค่าอ้างอิงจากฟอร์ม/ผลรอบก่อนแล้ว (ตรวจเฉพาะยอดรวม) ที่ยัง `failed`: 1312 (OCR หลอนในแถบแบนเนอร์), 1315 (ดูข้างล่าง)

ขั้นเตรียมภาพใช้ภาพล้วน ไม่เรียก OCR ไม่ทิ้งส่วนที่มีหมึก (สายงานคัดส่วนด้วย OCR รุ่นก่อนถูกถอดออกจากโค้ดแล้ว)

> ทางเลือกของขั้นนี้: คำสั่ง `regions` แบ่งเป็น region / ตาราง → ช่อง → key/value แบบ learning/preprocess_finance ผลแยกโฟลเดอร์ `regions/` ไม่แตะผังนี้ ส่งเข้า OCR ได้ด้วย `--layout regions` แต่วัดแล้วฟิลด์ขาด 26 เทียบกับ 14 ของผังนี้ ดู [03-regions.md](03-regions.md)

## ลำดับและไฟล์ (flow หลัก)

คำสั่งเดียวรันครบ: `python -X utf8 -m fin_extractor sections data/01_input/<ชุด> [--variant luma] [--profile <ชื่อ>] [--from <ขั้น>] [--to <ขั้น>] [--only <เลขไฟล์>] [--redo]`
ขั้นที่ผลของมันยังใช้ได้ถูกข้าม (กติกาใน `src/fin_extractor/sections/flow.py`): layout ข้ามถ้าพารามิเตอร์ตรงและผังใหม่กว่าภาพ final · images ข้ามถ้า `index.json` ตรงกับผัง · ocr ข้ามถ้ามีผลที่ลายนิ้วมือผังตรงและครบ (ไม่โหลดโมเดลเลยถ้าข้ามทุกไฟล์) · extract รันใหม่ทุกครั้ง (CPU เร็ว)

| ขั้น | `--from/--to` | สคริปต์ที่รันเดี่ยวได้ | Input | Output (ใต้ `data/`) | โค้ด |
|---|---|---|---|---|---|
| 2 | `preprocess` | `fin_extractor preprocess` | `01_input/<ชุด>/<ไฟล์>.pdf` | `02_preprocess/<ชุด>/default/final/<ไฟล์>/<ไฟล์>_p1.png` (ภาพสีทั้งหน้า ตรงแล้ว) + `manifest.json` | `preprocessing/`, `stages.py` |
| 3a | `layout` | `scripts/sections/make_section_layouts.py` | ภาพ `final/` | `03_sections/<ชุด>/default/layout/<ไฟล์>.json` (`layout_sections`, `layout_params`) + `<ไฟล์>_layout.png` ภาพตรวจด้วยตา | `sections/layout.py`, `sections/build.py` |
| 3b | `images` | `scripts/sections/make_clean_sections.py` | `final/` + ผัง | `03_sections/<ชุด>/default/images/<วิธี>/<ไฟล์>/sNN.png` + `index.json` (ค่าตั้งต้นของ `sections` เขียนเฉพาะวิธีที่ใช้ สคริปต์เขียนทั้ง luma/flat/bin) | `sections/images.py`, `sections/build.py` |
| 4 | `ocr` | `scripts/sections/run_sections.py` | ภาพใน `images/<วิธี>/` + ผัง | `04_ocr/<ชุด>/openthai/<วิธี>/<ไฟล์>/` `<ไฟล์>_p1.sections.json` `.md` `.chunks.json` | `sections/read.py` |
| 5 | `extract` | `fin_extractor extract ... --engine <engine> --variant <วิธี>` | `.md` ของขั้น 4 | `05_extract/<ชุด>/openthai/<วิธี>/rules/<ไฟล์>_p1.json` + `manifest.json` | `pipeline.py`, `extraction/`, `validation/` |

ขั้น 5 ใช้ CPU ล้วน (`--llm off` = rules ค่าตั้งต้น) ไม่อ่านภาพ อ่านเฉพาะข้อความรายส่วนที่ขั้น 4 เก็บไว้ ไฟล์ที่ยังไม่มีข้อความดิบถูกข้ามพร้อมข้อความบอก
`--variant color` ตัดจากภาพสีใน memory (ไม่มีขั้น images) ผลอยู่ `04_ocr/…/color/` · วิธีอื่นแยกโฟลเดอร์ `…/luma/` `…/flat/` `…/bin/` ไม่ทับกัน (ทั้งในขั้น 3b, 4, 5)

ตัวอ่านรับ **ภาพทีละส่วน** ได้ข้อความทีละก้อน สคริปต์เก็บแยกต่อส่วนใน `sections.json` และต่อกันตามลำดับอ่านใน `.md`
(ป้ายแต่ละท่อนเป็นคอมเมนต์ HTML `<!-- sNN kind -->` ที่ rules ตัดทิ้งจากตัวบรรทัดแต่ใช้บอก `source_chunk` ของ remark) ป้ายกับค่าที่อยู่คนละส่วนจึงอยู่ใกล้กันในไฟล์ แต่ไม่มีการจับคู่จากตำแหน่ง

ทดลองโดยไม่ทับผลจริง: ทุกคำสั่งรับ `--config <ไฟล์>` ที่เปลี่ยน `paths.data_dir` ได้ (ใช้ตรวจว่า refactor ไม่เปลี่ยนผล: สร้างผัง+ภาพลง data_dir ชั่วคราวแล้วเทียบไบต์กับของเดิม)

## ภาพผ่านอะไรบ้าง ทีละขั้น (2 → 3a → 3b → 4 → 5)

หัวข้อนี้ไล่ตามภาพหนึ่งหน้าตั้งแต่ออกจาก preprocess จนกลายเป็นข้อความที่สกัดได้ เพื่อให้เห็นว่า **Otsu**, **luma**, **flat**, **bin** อยู่ตรงไหนและต่างกันอย่างไร
สรุปสั้นที่สุด: **Otsu ใช้หา "ตัดตรงไหน" (ขั้น 3a) ส่วน luma / flat / bin คือ "ภาพแบบไหนที่ส่งให้ OCR อ่าน" (ขั้น 3b)** สองเรื่องนี้แยกกัน ภาพ Otsu ไม่เคยถูกส่งเข้า OCR

```
02 final/ ภาพสีทั้งหน้า (ความละเอียดเต็ม)
   │
   ├─► 3a layout   ย่อเป็นสำเนาทำงาน 1600 px → เทา → Otsu (ขาว-ดำ) → หาเส้นตาราง/แถวว่าง → ผัง (bbox ของแต่ละ section)
   │                 └─ ภาพ Otsu ใช้คิดเท่านั้น ไม่บันทึก ไม่ส่ง OCR
   │
   └─► 3b images   ใช้ bbox จากผัง ตัดจาก "ภาพสีเต็ม" (ไม่ใช่จากภาพ Otsu) → แปลงเป็น luma | flat | bin → sNN.png
                     │
                     ▼
       4 ocr       engine อ่านภาพทีละ section ของวิธีที่เลือก → .sections.json → ต่อเป็น .md + .chunks.json
                     │
                     ▼
       5 extract   rules (หรือ LLM) อ่าน .md → JSON ตาม schema (ไม่แตะภาพแล้ว)
```

### ขั้น 2 → อินพุตของขั้น 3: ภาพ `final/`

ภาพสีทั้งหน้าที่หมุนให้ตั้งตรงและแก้เอียงแล้ว (`02_preprocess/<ชุด>/<profile>/final/<ไฟล์>_p1.png`) **ไม่ได้ทำเป็นเทาหรือขาว-ดำ** ในขั้นนี้ (preprocess คงสีไว้ ดู [02-preprocessing.md](02-preprocessing.md)) เพราะการเลือกว่าจะส่งภาพแบบไหนให้ OCR ทำทีหลังแยกต่อ section ในขั้น 3b
ถ้าตัวตรวจทิศล้ม ภาพตะแคงจะไหลต่อทุกขั้นโดยไม่มีสัญญาณ ตรวจ `orientation_error` ใน `manifest.json` ก่อนเชื่อผล (ดูหัวข้อสุดท้ายของหน้านี้)

### ขั้น 3a `layout`: หาว่าจะตัดตรงไหน (ที่นี่เท่านั้นที่ใช้ Otsu)

ทำบน **สำเนาทำงาน** ไม่ใช่ภาพจริง (`build.build_layouts` → `layout.layout_sections`):

1. **ย่อ** ให้ด้านยาว 1600 px (`layout.WORK`) ภาพที่เล็กกว่านี้ไม่ขยาย ใช้คิดเร็วขึ้นและให้ขนาด kernel ทุกตัวมีความหมายเดียวกันทุกใบ
2. **เทา** ด้วย `enhance.to_gray` (สูตร luma เดียวกับข้อ 3b ข้างล่าง)
3. **ขาว-ดำด้วย Otsu** (`preprocessing/binarize.otsu`): เบลอ Gaussian 3×3 กันจุดรบกวน แล้วหาค่าตัดด้วย Otsu
   - **Otsu คืออะไร:** วิธีมาตรฐานหาค่าตัดขาว-ดำอัตโนมัติ ดู histogram ความสว่างทั้งภาพ แล้วเลือกค่าที่แบ่งพิกเซลเป็นสองกลุ่ม (หมึก / กระดาษ) ให้แต่ละกลุ่มกระจายตัวน้อยที่สุด ไม่ต้องตั้งเลขเอง ใช้ค่าเดียวทั้งภาพ จึงเหมาะกับสแกนที่แสงสม่ำเสมอ
   - ผลคือภาพ **หมึกดำบนพื้นขาว** ใช้แค่หาโครงสร้าง ไม่บันทึกเป็นไฟล์และไม่ส่ง OCR
4. **หาเส้นตาราง** (`line_masks`): morphological opening ด้วย kernel ยาว 1/30 ของด้านภาพ เหลือแต่เส้นแนวนอน/แนวตั้งยาว ๆ (ตัวอักษรสั้นกว่า kernel จึงหายไป)
5. **หาก้อนตาราง** (`table_regions`): กลุ่มเส้นแนวนอน+แนวตั้งที่เชื่อมกันและใหญ่ ≥ 2% ของหน้า แล้ว **ตัดกรอบครอบ** (`drop_frames`) ทิ้ง (กรอบฟอร์มทั้งใบที่มีตารางอื่นอยู่ข้างใน)
6. **หมึกสำหรับหาแถวว่าง** (`text_ink`): หมึกทั้งหมด **ลบเส้นตารางออก** ก่อน ไม่งั้นเส้นตั้งที่พาดทุกแถวทำให้ไม่มีแถวว่างให้ตัดเลย
7. **จุดตัดผู้สมัคร** (`--table-mode rows` ค่าตั้งต้น): ขอบบน/ล่างของทุกตาราง + เส้นแนวนอนที่ยาว ≥ 80% ของความกว้างตาราง (`table_rules`) + (ถ้าเปิด `--dotted-rules`) ใต้เส้นประ
8. **ตัดได้จริงเฉพาะแถวที่ว่างตลอดความกว้างหน้า** (`band_cuts`: หมึก < 0.2% ของความกว้าง) จึงไม่ตัดผ่านข้อความข้างตาราง ป้ายกับตัวเลขของแถวเดียวกันอยู่ภาพเดียวกัน
9. **ตัดแถบสูงเป็นท่อน** (`split_rows`): แถบที่สูงเกิน 30% ของหน้า (`MAX_PIECE_FRAC`) ตัดที่แถวว่างระหว่างบรรทัดที่ใกล้จุดแบ่งเท่า ๆ กันที่สุด ไม่ตัดกลางบรรทัด ไม่มีแถวว่างก็ยอมให้สูงเกิน ท่อนมี `part`/`parts`
10. **ทิ้งแถบว่าง**: แถบที่ไม่มีชิ้นหมึกขนาด ≥ 8 px ติด `keep: false` (ไม่ส่ง OCR แต่ยังอยู่ในผังเพื่อให้ id ต่อเนื่อง)
11. **เรียงลำดับอ่าน** บนลงล่าง ซ้ายไปขวา แล้วตั้ง id `s00`, `s01`, …

ผล: `03_sections/<ชุด>/<profile>/layout/<ไฟล์>.json` (bbox อยู่บนพิกัดสำเนา 1600 px พร้อม `layout_params`) และ `<ไฟล์>_layout.png` ภาพกรอบสีไว้ตรวจด้วยตา
ตัวเลข 1/30, 2%, 80%, 0.2%, 30%, 8 px เป็น **ค่าทดลอง** ที่วัดบนสแกน 18 ใบ ไม่มีเฉลย (ดูค่าคงที่และเหตุผลใน `sections/layout.py`)

### ขั้น 3b `images`: ภาพแบบไหนที่ส่งให้ OCR (luma / flat / bin)

1. **ตัดจากภาพสีเต็ม** (`crops.iter_section_crops` → `layout.crop_full`): คูณ bbox ของผังกลับเป็นพิกัดภาพจริง แล้วตัดจากภาพ `final/` ความละเอียดเต็ม **ไม่ได้ตัดจากภาพ Otsu หรือสำเนา 1600 px** ตัวอักษรจึงคมเท่าต้นฉบับ
2. **แปลงแต่ละ section เป็นวิธีที่เลือก** (`build.build_images`) เขียนที่ `03_sections/<ชุด>/<profile>/images/<วิธี>/<ไฟล์>/sNN.png` + `index.json` (บอก id, bbox, ขนาด และไฟล์ของแต่ละ section) แต่ละวิธีแยกโฟลเดอร์ ไม่ทับกัน

| วิธี | ขั้นตอนข้างใน (โค้ด) | ภาพที่ได้ | ข้อดี | ข้อเสีย |
|---|---|---|---|---|
| **`luma`** (ค่าตั้งต้น) | แปลงสีเป็นเทาด้วยสูตรความสว่างมาตรฐาน Y = 0.299R + 0.587G + 0.114B (`enhance.to_gray` = `cv2.COLOR_BGR2GRAY`) ไม่ทำอย่างอื่น | เทา เหมือนภาพสีที่สุด | ไม่ทิ้งข้อมูลอะไร เส้นบาง จุดทศนิยม ตัวอักษรจาง ยังอยู่ครบ | ตราประทับ ลายน้ำ แถบสี ยังเห็นเป็นสีเทาปนกับข้อความ |
| **`flat`** | (1) เทาแบบ "ช่องสว่างสุด" = max(R,G,B) (`gray_value_channel`): หมึกดำมืดทุกช่องจึงยังดำ แต่สีอื่น (ฟ้า แดง เขียว) มีอย่างน้อยหนึ่งช่องสว่าง จึงกลายเป็นเกือบขาว (2) ประมาณพื้นหลังด้วย morphological closing วงรีขนาด ≈ 4% ของด้านสั้น (อย่างน้อย 15 px ใหญ่กว่าตัวอักษร ตัวอักษรจึงหายจากภาพพื้นหลัง) แล้วเบลอ (3) หารภาพด้วยพื้นหลัง ลบเงาและสีพื้น (4) ยืดคอนทราสต์จาก percentile ที่ 1 (`flatten_background`) | เทา พื้นขาวเรียบ ตัวหนังสือเข้ม | ตัดลายน้ำ/ตราสี/เงาออก | ตัวอักษรสีอ่อนหรือหมึกสีอาจจางตามไปด้วย |
| **`bin`** | (1) แปลงเป็นสี Lab (2) ประมาณ "สีพื้นรอบข้าง" ของทุกจุด: ย่อภาพ 1/4 แล้ว median หน้าต่าง 31 (≈ 124 px บนภาพจริง กว้างกว่าเส้นตัวอักษรหัวเรื่อง) แล้วขยายกลับ (3) วัดระยะสี (Euclidean ใน Lab) ของแต่ละพิกเซลจากสีพื้นนั้น (4) หาค่าตัดของ **ระยะสี** ด้วย Otsu แต่ไม่ต่ำกว่า 28 (`BIN_FLOOR` กันรอยยับของกระดาษเมื่อ Otsu ได้ค่าต่ำ) (`binarize_inverted`) | ขาว-ดำกลับสี **ตัวอักษรขาว พื้นดำ** | ไม่ขึ้นกับสี: ตัวดำบนขาว ตัวขาวบนแถบเขียว/น้ำเงิน และตัวสีบนพื้นสี ได้ผลแบบเดียวกัน | ทิ้งรายละเอียดระดับเทาทั้งหมด ขอบแถบสีมุมโค้งเกิดเส้นบาง ๆ และ OpenThai อ่านได้แย่กว่าชัดเจน (ตารางข้างล่าง) |
| `color` (ไม่มีขั้น 3b) | ไม่เขียนไฟล์ ขั้น 4 ตัดจากภาพสี `final/` ในหน่วยความจำ | สี | ไม่แปลงอะไรเลย | ไม่มีไฟล์ภาพให้เปิดดูย้อนหลัง |

- **Otsu ใน `bin` ต่างจากใน 3a:** ใน 3a ตัดที่ "ความสว่าง" ของทั้งหน้า ใน `bin` ตัดที่ "ระยะสีจากพื้นรอบข้าง" ของแต่ละ section ชื่อวิธีเดียวกันแต่ใช้กับค่าคนละอย่าง
- **`--drop-empty-rows`** (ใช้กับ `bin` เท่านั้น ไม่ใช่ค่าตั้งต้น): ทาดำแถวตารางที่ช่องตัวเลขว่าง section ที่ทาดำหมดไม่มีไฟล์ (`file: null`) ขั้น 4 ข้าม รายละเอียดในหัวข้อ "แบบ bin" ข้างล่าง
- คำสั่ง `sections` เขียนเฉพาะวิธีที่เลือกด้วย `--variant` ส่วน `scripts/sections/make_clean_sections.py` เขียนครบทั้งสามวิธี
- ภาพทุกวิธีมาจาก **ผังเดียวกัน** (bbox เดียวกัน) จึงเทียบข้ามวิธีได้ตรง ๆ `index.json` ต้องตรงกับผังปัจจุบัน ไม่งั้นขั้น 4 หยุดก่อนโหลดโมเดล

### ขั้น 4 `ocr`: อ่านทีละ section

engine ที่เลือก (`--engine openthai|typhoon|paddle|oxr`) อ่าน `images/<วิธี>/<ไฟล์>/sNN.png` ทีละภาพตามลำดับใน `index.json` (section ที่ `keep: false` หรือไม่มีไฟล์ถูกข้าม) **ไม่มีการอ่านทั้งหน้า**
ผลอยู่ที่ `04_ocr/<ชุด>/<engine>/<วิธี>/<ไฟล์>/`: `.sections.json` (ข้อความรายส่วน + ลายนิ้วมือของผัง) → `.md` (ทุกส่วนต่อกันตามลำดับอ่าน มี `<!-- sNN kind -->` นำหน้าแต่ละท่อน) → `.chunks.json` (ท่อนข้อความ ↔ ภาพ section ↔ บรรทัดใน `.md`)
วิธีของภาพเป็นส่วนหนึ่งของพาธ (`…/luma/` `…/flat/` `…/bin/`) ผลของแต่ละวิธีจึงไม่ทับกัน

### ขั้น 5 `extract`: สกัดจากข้อความ

อ่านเฉพาะ `.md` ของขั้น 4 (ไม่แตะภาพ ไม่ใช้ GPU) แปลงเป็นบรรทัด แล้ว rules (หรือ LLM ถ้า `--llm on`) สกัดเป็น JSON ที่ `05_extract/<ชุด>/<engine>/<วิธี>/<extractor>/` คอมเมนต์ `<!-- sNN -->` ถูกตัดออกจากบรรทัด แต่ใช้บอก `source_chunk` ของ `remark` ว่าข้อมูลมาจาก section ไหน ([05-extraction.md](05-extraction.md))

### เลือกวิธีไหน

เทียบ 3 วิธีกับ OpenThai, rules ล้วน, 18 ใบ (ตารางเต็มอยู่ในหัวข้อ "แบบ bin" ข้างล่าง): ฟิลด์ที่ขาดรวม **luma 14** · flat 16 · bin 28 จึงตั้ง **luma เป็นค่าตั้งต้น**
ข้อจำกัด: วัดแค่ "สกัดเจอครบไหม" ไม่มีเฉลยจึงไม่รู้ว่าค่าถูกหรือไม่ และวัดกับ OpenThai ตัวเดียว ถ้าเป็น Typhoon / Paddle ลำดับอาจต่างไป (ยังไม่ได้วัด) ลองเองได้ด้วย `sections --engine <ตัวนั้น> --variant flat` แล้ว `compare`

## แบบ `bin`: ขาวดำ ตัวอักษรขาว กระดาษดำ

`make_clean_sections.py` เขียน `images/bin/<ไฟล์>/sNN.png` เพิ่มจาก luma/flat (flow `sections --variant bin` เขียนเฉพาะ bin) · อ่านด้วย `sections --variant bin` (ผลอยู่ `04_ocr/<ชุด>/<engine>/bin/`) · สกัดซ้ำ `extract --variant bin`
- **ไม่ใช้ความสว่าง** ตัดสินจากระยะสี (Lab) ของพิกเซลจากสีพื้นรอบข้าง (median หน้าต่างใหญ่) แล้ว threshold (Otsu ขั้นต่ำ `BIN_FLOOR`) ตัวดำบนขาว ตัวขาวบนแถบเขียว/น้ำเงิน ตัวสีบนพื้นสี ได้ผลแบบเดียวกัน ดูด้วยตาบน 1306 s07/s20, 1310, 1312 s02, 1317 s03, 1318 s03, 1319 s02 ผลวัดกับ OpenThai อยู่ในตารางข้างล่าง (แย่กว่า luma)
- จุดอ่อน: ขอบของแถบสีมุมโค้ง (1312) เกิดเส้นบางตามขอบ
- `--drop-empty-rows` (ใช้กับฟอร์มอย่าง 1307 เท่านั้น ไม่ใช่ค่าตั้งต้น): ทาดำแถวตารางที่ช่องตัวเลขว่าง เหลือแถวที่มีค่าพร้อมป้ายของมัน จากภาพล้วน (ไม่ใช้ OCR) หาคอลัมน์ป้ายจากเซลล์กว้างสุดตามเส้นตั้ง ตัดจุดไข่ปลา/เศษเส้นด้วยขนาดชิ้นหมึก (ค่าวัดบน 1307 ที่เดียว ดูค่าคงที่ `MIN_GLYPH_*` `DOT_MAX_H` ใน `sections/images.py`) ใช้คอลัมน์เดียวกันทั้งตาราง (ส่วนที่ตัดมาไม่เห็นเส้นตั้งครบ) ส่วนที่ทาดำหมดไม่มีไฟล์ `bin` ตัวอ่านข้าม 1307: เหลือแถวที่ 1 (วันที่ 05/10/2026, 2,000.00, 60.00), หัวคอลัมน์ และแถวรวม · ผิดพลาดที่เห็น: แถว (1.2) ท้ายส่วน s01 ถูกเก็บไว้ทั้งที่ว่าง (เศษที่ขอบตัด) ตรวจกับใบอื่นแค่ 1307 ใบเดียว
- **ผลเทียบทั้ง 3 แบบ (OpenThai, rules ล้วน, 18 ใบ, ไม่มีเฉลย วัดแค่ความครบ):**

| | luma | flat | bin |
|---|---|---|---|
| ฟิลด์ที่ขาดรวม | **14** | 16 | 28 |
| เช็คที่ไม่ผ่านรวม | **10** | 14 | 11 |
| ใบที่ `failed` | 2 (1312, 1315) | **1** (1315) | 4 (1307, 1317, 1318, 1319) |

  **luma ดีที่สุดโดยรวม จึงเป็นค่าตั้งต้น** bin ดีกว่าเฉพาะ 1315 (ขาดแค่ entry_no) แย่กว่ามากที่ 1318/1319 (ขาด 5 ฟิลด์ ส่วนหัวอ่านได้สั้นลงมาก เช่น 1318 s00 16 ตัวอักษร ต่อ 249 ของ luma) และ 1320 สันนิษฐานว่า OpenThai ไม่ได้ฝึกกับภาพขาวบนดำ (ยังไม่ได้ทดสอบ) ผล luma/flat ของบางใบเป็นผลเก่าที่ข้ามเพราะมีอยู่แล้วและผังตรงกัน
- **1307 + `--drop-empty-rows` ยังตก `failed`**: ป้ายยอดอยู่ครบ แต่ OpenThai อ่านเส้นคั่นสตางค์ที่ติดตัวเลขเป็น `2,000:00` ซึ่ง rules ไม่รับ (luma อ่านเป็น `2,000 .00` ซึ่ง rules ซ่อมได้) ลองลบเส้นตั้งที่เหลือทิ้งแล้ว ผลเปลี่ยนเป็น `2,000/00` ยังไม่ผ่าน (จุดทศนิยมติดเส้นถูกลบไปด้วย) จึงถอนการลองนั้นออก **ยังไม่มีทางแก้ที่ใช้ได้** ถ้าต้องการแถวที่มีค่าอย่างเดียวให้ใช้ luma แล้วกรองแถวหลัง OCR แทน


## เทียบข้ามวิธีแบบแฟร์: `fin_extractor compare`

`python -X utf8 -m fin_extractor compare data/01_input/<ชุด> [--variants luma flat bin] [--out ตาราง.md]` อ่าน manifest ของแต่ละวิธีแล้ว **ติดธงแถวที่เทียบไม่แฟร์และไม่นับในยอดรวม**: `ผังต่างกัน` (ลายนิ้วมือผังใน `.sections.json` ไม่ตรงกัน) · `ผลเก่ากว่าผัง` · `drop-empty-rows` (ภาพวิธีนั้นลบแถวตารางว่าง) · `ไม่มีผล` เพื่อไม่ให้เกิดตารางปนกันแบบรอบแรก (`src/fin_extractor/sections/compare.py`)
ผลบน 18 ใบ (ธง 3 ใบ: 1306 และ 1316 ผล luma เก่ากว่าไฟล์ผัง, 1307 bin ใช้ `--drop-empty-rows`; ยอดรวม 15 ใบที่เหลือ): ฟิลด์ที่ขาด luma 13 · flat 14 · bin 23, failed 2 / 1 / 3 ลำดับเหมือนตารางเดิม (luma ดีสุด) ยังวัดแค่ความครบ ไม่ใช่ความถูก

## ไฟล์ chunks: ข้อความท่อนนี้มาจากภาพ section ไหน

`run_sections.py` เขียน `<ไฟล์>_p1.chunks.json` ข้างไฟล์ `.md` และ `.sections.json` ใน `04_ocr/<ชุด>/<engine>/<วิธี>/<ไฟล์>/` (สร้างใหม่จากผลที่มีอยู่ได้โดยไม่ใช้ GPU: `run_sections.py --variant <วิธี> --markdown-only`) `extract` อ่านเฉพาะ `.md` จึงไม่กระทบการสกัด

ต่อหนึ่งท่อนข้อความ (`chunks[]`):
- `section`, `kind`, `part`/`parts`: ท่อนมาจากส่วนไหนของผัง
- `md_lines`: ช่วงบรรทัดของท่อนใน `.md` (นับจาก 1 รวมบรรทัดคอมเมนต์ `<!-- sNN ... -->`)
- `text`: **ข้อความที่ได้จากภาพนั้น** (ภาพ `image` → `text` อ่านคู่กันได้ในไฟล์เดียว)
- `image`: ภาพที่ส่งเข้าตัวอ่าน (สัมพัทธ์กับ `data/`, เช่น `03_sections/finance_doc_scan/default/images/luma/<ไฟล์>/s05.png`) `--variant color` ไม่มีไฟล์ ตัดจากภาพ final ตาม `page_bbox_xywh` (บนสำเนาด้านยาว 1600 px)
- `chars`, `seconds`, `truncated`: ขนาดข้อความ เวลาอ่าน และธงชนเพดาน token
- `script_mix`: จำนวนอักขระไทย / ละติน / ตัวเลขในข้อความที่ตัวอ่านตอบ (ไม่นับแท็ก HTML) **นับจากผล ไม่ใช่การเลือกภาษาของโมเดล** ดู [12 หัวข้อ 2.1](04-openthai-ocr.md#21-เลือกภาษาไทยอังกฤษอย่างไร)

`not_read[]`: ส่วนที่ไม่มีข้อความ พร้อมเหตุผล (`blank` = ผังตัดทิ้งหรือ `bin` ทาดำหมด, `error`, `no text`)

## ผังแบบ fill-aware (`--fill-aware`, ไม่ใช่ค่าตั้งต้น)

**ที่มาของปัญหา:** ผังเดิมหา "แถวว่าง" จากหมึกเข้มบนพื้นสว่าง (Otsu) ตัวอักษรขาวบนแถบสีจึงดูเป็นพื้นว่าง ผังตัดผ่านแถบนั้นได้ 1306 s01/s02: แถบเทา "Receipt" ถูกตัดเหลือเสี้ยวสูง 30 px ให้ OCR (luma) โมเดลเดาข้อความเองออกมา (`เป็นต้องการส่วนระบุได้ … ๒๕๖๑`) ข้อความนี้ไม่มีที่อื่นในหน้าและไม่มีในผล flat/bin ของไฟล์เดียวกัน (ตามรอยด้วย `chunks.json`)

**วิธีแก้ที่ลอง** (`sections/images.fill_masks` + `layout_sections(fill_region=, fill_text=)`): พื้นสี = ที่สีพื้นรอบข้างต่างจากสีกระดาษของหน้าเกิน `BIN_FLOOR` ตัวอักษรบนพื้นสีนับเป็นหมึก และแถวในพื้นสีไม่นับเป็น "แถวว่าง" จึงไม่ตัดผ่าแถบ (เทสต์: `test_fill_aware_layout_does_not_cut_through_a_coloured_banner`)

**ผลวัด (OpenThai luma, rules ล้วน, ไม่มีเฉลย):** ผังเปลี่ยน 6 ใบจาก 18 (1306 1310 1312 1317 1318 1319) ส่วนน้อยลงและใหญ่ขึ้น (1306: 23 → 15 ส่วน, 1317/1318/1319 → 4 ส่วน) OCR ใหม่เฉพาะ 6 ใบนี้ แล้วสกัด
| ไฟล์ | ฟิลด์ที่ขาด เดิม → fill-aware |
|---|---|
| 1306 | invoice_no → vendor.name, invoice_no (แย่ลง 1) |
| 1317 | invoice_no → ไม่ขาด (ดีขึ้น 1) |
| 1310 1312 1318 1319 | ไม่เปลี่ยน (1312 ยัง `failed`) |
| รวม 6 ใบ | 6 → 6 |

ข้อความที่เดาเองของ 1306 หาย แต่ผลรวมไม่ดีขึ้น (ส่วนใหญ่ขึ้นลงจากการที่ส่วนใหญ่ขึ้น OCR อ่านต่างไป) และส่วนที่ถูกตัดกลางกล่องข้อมูลของ 1317 (ตัดที่ `max_piece_frac` เพราะไม่มีแถวว่างเหลือ) ผังเดิมทั้ง 18 ใบจึงยังเป็นค่าตั้งต้น (ผังเก่าไม่มีคีย์ `fill_text_ink` = แบบเดิม) ใช้เมื่อต้องการ: `sections ... --fill-aware` หรือ `make_section_layouts.py --fill-aware` **ยังไม่ได้ลองวิธีรวมแถบที่เตี้ยกว่าบรรทัดข้อความ** (วัดแล้วแถบที่ปัญหา 30 px สูงกว่าความสูงตัวอักษรอยู่ดี จึงไม่ช่วยกรณี 1306)

## ผังตัดตามเส้นประ (`--dotted-rules`, ไม่ใช่ค่าตั้งต้น)

ฟอร์มอย่าง 50 ทวิ (1307, 1321, 1323) แบ่งแถวรายการด้วย **เส้นประ** ที่มีเฉพาะคอลัมน์ตัวเลข `line_masks` เก็บได้แต่เส้นทึบ จึงไม่เจอเส้นแบ่งแถวเลย ผังตกไปใช้ `split_rows` ที่ตัดตามความสูง (1307 ได้ 5 ส่วน ตัดกลางรายการ)
`dotted=True` (`layout.py`: `thin_joined` → `dotted_rules` → `cuts_below_rules`): เอาเฉพาะหมึกบาง (สูง < `DOT_THIN` px) ขยายแนวนอน `DOT_GAP` px ให้จุดต่อกัน เลือกแถวที่ช่วงต่อเนื่องยาว ≥ `DOT_RUN` ของความกว้างตาราง (ไม่ใช่ 0.8 เหมือนเส้นทึบ เพราะเส้นประไม่พาดป้ายฝั่งซ้าย) แล้วตัดที่กลางแถวว่างแรกใต้เส้น (เส้นประอยู่ที่ฐานข้อความของแถว) ยังบังคับว่าต้องเป็นแถวที่ว่างทั้งความกว้างหน้า จึงไม่ตัดข้อความฝั่งป้าย
ค่า `DOT_GAP` 9 · `DOT_THIN` 5 · `DOT_RUN` 0.3 **เป็นค่าทดลอง** เลือกจากการดูโปรไฟล์ความครอบคลุมของ 1307 เท่านั้น ยังไม่ได้เทียบค่าอื่นบนทั้งชุด
ผลบน 18 ใบ (ดูแค่ผัง ยังไม่ได้รัน OCR): จำนวนส่วนเปลี่ยนใน 10 ใบ (1307 5→12, 1321 5→14, 1323 7→16, 1310 5→9, 1311 7→14, 1306 13→14, 1308/1309/1320/1322 +1 ถึง +2) 1312 1315–1318 ผังเท่าเดิม ดูภาพผัง 1307 1311 1323 แล้วจุดตัดอยู่ระหว่างบรรทัด ไม่พาดข้อความ ข้อจำกัดที่เห็น: 1307 รายการ 1–4 ที่เส้นประจางยังไม่ถูกแยก และ 1323 ถูกตัดละเอียดจนส่วนเล็กมาก

**ผล OpenThai + rules (luma, ไม่มีเฉลย, เทียบกับผังเดิมในโฟลเดอร์ข้อมูลชั่วคราว):** 1307 และ 1321 ฟิลด์ที่สกัดได้เท่าเดิมทุกตัว (20 และ 24 ฟิลด์ ต่างกันแค่ตัวอักษรที่ OCR อ่านเพี้ยน) **ไม่เห็นว่าดีขึ้น** · 1323 **แย่ลง** (19 → 13 ฟิลด์: วันที่หาย รายการแรกได้ภาษี 3,187.50 แทนยอดจ่าย 106,250.00 และ `vendor.tax_id` กลายเป็นเลขของผู้ถูกหักภาษี) เพราะ OCR ของส่วนกล่องผู้จ่ายอ่านเลข 13 หลักได้ 12 หลัก checksum ไม่ผ่าน rules จึงไปหยิบเลขอีกฝ่าย (รันซ้ำแล้ว: ผังเดิม 2 รอบได้ผลเหมือนกันทุกฟิลด์ และผังเส้นประรอบที่สองได้ผลเดิม จึงเป็นผลของผัง ไม่ใช่ความแปรปรวนของ OCR) ตัวอย่างเพียง 3 ใบ สรุปได้แค่ว่า **ยังไม่มีหลักฐานว่าคุ้ม จึงไม่เปิดเป็นค่าตั้งต้น**

## กฎการแบ่ง (`src/fin_extractor/sections/layout.py`)

ทำบนสำเนาด้านยาว 1600 px (Otsu) แล้วตัดภาพจริงจากภาพเต็มสี ค่าตั้งต้น `--table-mode rows`
1. **แถบแนวนอนเต็มความกว้างหน้า** จุดตัดผู้สมัคร = ขอบบน/ล่างของตาราง + เส้นแนวนอนยาวเต็มตาราง (`table_rules`) ตัดเฉพาะที่ **แถวนั้นว่างตลอดความกว้างหน้า** (`band_cuts`) ไม่ตัดผ่านข้อความข้างตาราง ป้ายที่อยู่ซ้ายของกล่องตัวเลข (เช่น กล่องยอดรวมของ 1306) จึงอยู่ภาพเดียวกับค่าของแถวนั้น แถบคลุมทั้งหน้าพอดี ไม่มีหมึกตกหล่น (วัด 0% ทุกใบ)
2. **ตัดกรอบครอบ** (`drop_frames`): ตารางที่มีตารางอื่นอยู่ข้างในคือกรอบของฟอร์ม ตัดทิ้งก่อนหาเส้น ข้อมูล 18 ใบ: ตารางซ้อนกัน 4 คู่ เป็นกรอบฟอร์มทั้งหมด
3. **ตัดแถบสูงเป็นท่อน** (`split_rows`): แถบที่สูงกว่า `MAX_PIECE_FRAC` = 0.3 ของหน้า ตัดที่แถวว่างระหว่างบรรทัด ไม่ตัดกลางบรรทัด ถ้าไม่เหลือช่องว่างก็หยุดตัด ท่อนมี `part`/`parts`
4. แถบที่ไม่มีหมึกเลยติด `keep=False` (ไม่ส่ง OCR)

โหมดอื่น: `--table-mode bands` (ตัดเฉพาะที่ขอบตาราง) · `whole` (ตารางทั้งก้อน ป้ายข้างตารางเป็นอีกภาพ) · `cells` (แตกเป็นช่องตามเส้น)

ดูผลด้วยตา: `..._layout.png` น้ำเงิน = แถบที่ส่วนใหญ่อยู่ในตาราง · ส้ม = แถบข้อความ · เขียว = ช่อง (โหมด cells) · แดงหนา = ว่าง (ไม่ส่ง OCR) เลขสีม่วง = id ส่วน

## ผลวัด (9 ใบ OpenThai luma, rules ล้วน)

**ขนาดท่อนสูงสุด** (วัดตอนที่โหมดตั้งต้นยังเป็น `whole` ค่า 0.3 ยังไม่ได้วัดซ้ำกับ `rows`)

| `MAX_PIECE_FRAC` | ฟิลด์ที่ขาดรวม | `failed` | หมายเหตุ |
|---|---|---|---|
| 0.5 | 9 | 0 | 1310 ขาดวันที่ (OpenThai ทิ้งกล่องหัวตารางเมื่อส่งตารางทั้งก้อน อ่านเฉพาะส่วนบนของตารางเดียวกันได้ครบ) |
| **0.3 (ค่าตั้งต้น)** | **7** | 0 | กู้วันที่ 1310 และวันที่/เลขที่ 1320 · **เสีย invoice_no ของ 1317** (บรรทัดเลขที่ใบกำกับอยู่หัวท่อน OCR อ่านได้แต่ป้าย) |
| 0.2 | 9 | 1 | 1307 ตก `failed` ตารางถูกตัด 4 ท่อน แถวยอดรวมไม่ปรากฏในท่อนใด |

**โหมดการแบ่ง** (ท่อน 0.3, luma) วัด 2 อย่าง: (1) ป้าย–ค่าของกล่องยอดรวมอยู่บรรทัดเดียวกันหลัง `markdown_to_lines` ไหม 22 คู่ที่อ่านจากภาพจริง (1306, 1308, 1310, 1312, 1317) (2) สถานะ rules

| โหมด | คู่ป้าย–ค่าตรงกัน | `failed` | ฟิลด์ที่ขาดรวม |
|---|---|---|---|
| `whole` (ตารางก้อนเดียว ป้ายข้างตารางเป็นอีกภาพ) | 13/22 | 0 | 7 |
| `bands` (ตัดที่ขอบตาราง) | 10/22 | 1 | 8 |
| **`rows` (ค่าตั้งต้น)** | **18/22** | 1 | 7 |

`rows` แก้ 1306 (ป้ายของกล่องยอดรวม 0/6 → 5/6, ขาดฟิลด์ 2 → 1) และ 1317 (0/3 → 3/3) แต่ **1312 แย่ลง** (3/3 → 0/3 และตก `failed`): แถบที่มีแบนเนอร์เขียว "สามพันเก้าร้อยสี่สิบเก้าบาทถ้วน" อยู่ข้างกล่องยอดรวม ทำให้ OpenThai หลอน ใส่ข้อความแบนเนอร์แทนป้าย "รวมเป็นเงิน"/"ภาษีมูลค่าเพิ่ม 7%" ผมไม่พบกฎจากภาพล้วนที่แยกกรณีนี้ (ไม่ควรรวม) ออกจาก 1306 (ควรรวม) ผู้ใช้เลือก `rows` เพราะแก้ปัญหาที่ต้องการตรง ๆ

**แบบภาพ** (ที่ 0.5): color / luma / flat ต่างกันแค่ 1310 (luma, flat ได้ยอดรวม color ไม่ได้) นอกนั้นเหมือนกันทุกฟิลด์ luma กับ flat แยกไม่ออกจากเกณฑ์นี้ จึงตั้ง luma เป็นค่าตั้งต้น (เอกสารเดิมบันทึกว่า flat เคยทำให้ตัวอักษรจางหายใน 1317 แต่ครั้งนี้ไม่เห็น)

**สิ่งที่พบระหว่างทาง**
- กฎลบช่องว่างก่อนทศนิยม (`"2,000 .00"` → `2,000.00`) ใน `markdown_to_lines` เดิม **ไม่เคยทำงาน** เพราะมีอักขระ backspace ฝังใน regex แก้แล้ว: 1307 (50 ทวิ) จาก `failed` เป็น `needs_review` ขาด 0 ช่อง
- ฟิลด์ที่ขาดที่เหลือส่วนใหญ่ไม่ใช่เรื่องภาพ: 1306 ชื่อผู้ขาย/เลขที่ (อ่านได้แต่ไม่มีป้ายที่ rules รู้จัก) · 1320 ลายมืออ่านเพี้ยน (วันที่ `12/16/2026` rules ปฏิเสธถูกต้อง) · 1312 มีป้าย "เลขที่" ไม่มีค่า

## ข้อจำกัด (อ่านก่อนอ้างตัวเลข)

- **ตัวอย่าง 9 ใบ ไม่มีเฉลย** ผลสกัดต่างกัน 1–2 ฟิลด์ต่อใบ อาจเป็นความผันผวนของตัวอ่านก็ได้ ไม่ได้ทำซ้ำเพื่อวัดความแปรปรวน ค่า 0.3 มาจากการเทียบ 3 ค่าเท่านั้น
- **`rows` ตัดแถบหัวคอลัมน์แยกบาง ๆ จากแถวรายการ** (เห็นใน 1306) และแถบที่มีแบนเนอร์ใหญ่ข้างกล่องเล็กทำให้ OCR หลอน (1312) การเลือกต่อใบไม่มีเกณฑ์ที่วัดมา
- ตัวชี้วัดคู่ป้าย–ค่าเป็น 22 คู่ใน 5 ใบ คู่คำป้ายเลือกจากที่ OCR สะกดตรงน่าจะ (ไม่ได้ผ่านเฉลยทางการ)
- **ท่อนหลังของตารางไม่มีหัวคอลัมน์ซ้ำ** ยังไม่ได้ทำ (ฟอร์มอย่าง 50 ทวิ บล็อกบนสุดไม่ใช่หัวตารางจริง การแปะซ้ำโดยเดาจะผิด) ใบรายการยาวมากอาจเสียหัวคอลัมน์ในท่อนหลัง
- **กฎกรอบ** ตัดสินจาก 18 ใบ เอกสารที่มีตารางจริงซ้อนตารางย่อยจะถูกแยกหัวออกจากแถว
- `--table-mode cells` ผู้ตรวจรายงานว่าอาจได้ช่องที่ซ้อนกันและ OCR ข้อความซ้ำ **ยังไม่ได้ยืนยันสาเหตุ** (ไม่ใช่โหมดตั้งต้น)
- ผล `sections.json` บันทึกลายนิ้วมือของผัง (id + bbox ของส่วนที่เก็บ) รอบถัดไปถ้าผังเปลี่ยนจะทำใหม่ทั้งไฟล์ ไม่ข้ามหรือต่อผลเก่า และ `--variant luma/flat` หยุดถ้า `images/<วิธี>/` ไม่ตรงกับผังปัจจุบัน (ตรวจก่อนโหลดโมเดล)
- **ตัวชี้วัด "ฟิลด์ที่ขาด" มองไม่เห็นค่าผิด** ตัวอย่างจริง: 1316 วันที่ถูกสกัดเป็น 2018-11-26 (วันที่ท้ายฟอร์ม "ลงวันที่ 26 พฤศจิกายน 2561") เพราะ OCR ไม่ได้อ่านบรรทัด "วันที่นำเข้า/ส่งออก 27-10-2569" ในผังปัจจุบัน (ผังท่อน 50% เคยอ่านได้ 2026-10-27) และเช็ค `date_range` ผ่านเพราะเป็นวันที่ที่เป็นไปได้ การเลือกค่า 0.3 / `rows` ใช้ตัวชี้วัดนี้ จึงอาจยังมีค่าผิดที่ไม่ถูกนับ
- **`rows` ตัดแถบหัวคอลัมน์ออกจากแถวรายการ** 1317: หัวตารางถูกตัดเป็นสองส่วน รายการสินค้าได้คำอธิบายที่ปนข้อความหัวคอลัมน์ และยอด 7,500.00 ถูกนับสองครั้ง (`items_sum` ไม่ผ่าน 15000 เทียบ 8025) ส่วนยอดรวมที่ OpenThai ตอบเป็นตาราง LaTeX แทน HTML (ขึ้นต้นด้วย tabular) rules ยังสกัดได้
- ผลสกัดต่อเข้า `extract` แล้ว (ขั้น 5) ไม่มีเฉลย ตัวเลขทั้งหมดวัดความครบ ไม่ได้วัดความถูก

## เหตุการณ์ที่ทำให้ผลผิดเงียบ ๆ: ตัวตรวจทิศล้ม (1315)

- `preprocess` เมื่อ 17 พ.ย. ได้ภาพ 1315 **ตะแคง 90°** (`orientation: 0`) เพราะตัวตรวจทิศของ Paddle โหลดไม่ได้ (`WinError 127` ที่ `cudnn_cnn64_9.dll`) **สาเหตุ (พบ 20 พ.ย.):** paddlex import `modelscope` ซึ่ง import torch พ่วงมา torch (cu128) ใช้ cuDNN 9.19 ส่วน paddlepaddle-gpu ล็อก cuDNN 9.15 ชื่อ DLL เดียวกันอยู่ใน process เดียวกันไม่ได้ **แก้แล้ว:** `ocr/paddle_engine.without_modelscope` กันไม่ให้ torch ถูกโหลดตอน import paddlex และคำสั่ง `sections` รัน preprocess แยก process รอบ 20 พ.ย. ตรวจทิศได้ครบ 18 ใบ (1315 หมุน 90° อัตโนมัติ) โค้ดเดิมคืน 0 เงียบ ๆ ผัง OCR และการสกัดของ 1315 ทำบนภาพตะแคงโดยไม่มีสัญญาณ
- แก้โค้ด: `orient.detect_orientation_checked` คืน (มุม, ข้อผิดพลาด) · `preprocess` บันทึก `meta.orientation_error` (เห็นใน `manifest.json`) และ CLI พิมพ์คำเตือน · `preprocess <ไฟล์> --orientation 90` สั่งทิศเอง ทำใหม่ไฟล์นั้นทันที (ไม่ต้อง `--force`) และไม่เก็บลง `settings.json` กัน `--force` ล้างทั้งโปรไฟล์
- 1315 แก้แล้วด้วย `--orientation 90` (ตรงกับค่าที่ตัวตรวจเคยตรวจได้ตอนแรก) ทำใหม่ผัง → ภาพย่อย → OCR → สกัด ภาพอ่านได้ปกติ แต่ยังตก `failed` ด้วยเหตุที่ต่างออกไป: **OCR ไม่ได้อ่านเลขฝั่งขวาของแถบ (0.00 / 149.16) เลย** และโปรไฟล์ศุลกากรของ rules คาดว่า `Special Entry Number : ค่า` อยู่บรรทัดเดียวกัน แต่ตารางแยกเป็นสองบรรทัด
- ข้อควรระวัง: ถ้าตัวตรวจล้มอีก ภาพตะแคงจะไม่ถูกจับ ตรวจ `manifest.json` หา `orientation_error` ก่อนเชื่อผลเสมอ (17 ใบที่เหลือตั้งตรงอยู่แล้ว ผลจึงไม่กระทบ)
