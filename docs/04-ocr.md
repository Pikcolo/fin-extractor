# ขั้นที่ 4: อ่านข้อความ (OCR)

> **ห้ามอ่านทั้งหน้า:** ทุก engine อ่านทีละภาพ section ผ่าน `python -m fin_extractor sections --engine openthai|typhoon|paddle|oxr` เท่านั้น
> (คำสั่ง `ocr` ถูกปิด `extract` สกัดจากข้อความรายส่วนที่เก็บไว้เท่านั้น) ตัวเลขผลวัด "ทั้งหน้า" ในเอกสารนี้เป็นบันทึกของรุ่นก่อน เทียบกับผลรายส่วนตรง ๆ ไม่ได้

การแบ่งหน้าเป็น section ดู [03-sections.md](03-sections.md) · OpenThai ดู [04-openthai-ocr.md](04-openthai-ocr.md) · OXR ดู [archive/oxr.md](archive/oxr.md)

## ตัวอ่านทุกตัวใช้ทางเดียวกัน (`src/fin_extractor/readers/`)

```python
from fin_extractor.readers import make_reader
res = make_reader("openthai", cfg).recognize(img)   # img = ภาพ BGR → ReadResult(engine, text, finish_reason, confidence)
```

- **สร้างตัวอ่าน:** `make_reader(engine, cfg)` ยังไม่โหลดโมเดล โมเดลโหลดตอนอ่านภาพแรก และไม่ import torch หรือ paddle ของตัวที่ไม่ได้เลือก
- **ค่าตั้ง:** อยู่ใน `configs/default.yaml` ใต้คีย์ชื่อเดียวกับ engine (`openthai:` `typhoon:` `paddle:` `oxr:`)
- **ผลรูปแบบเดียวกันทุกตัว** (`ReadResult` ใน `readers/base.py`):
  - `text`: Markdown (ตารางเป็น HTML) หรือบรรทัดล้วน แล้วแต่ engine ขั้นสกัดแปลงเป็นบรรทัดด้วย `markdown_to_lines` ตัวเดียวกันทุก engine
  - `finish_reason`: `"length"` เมื่อชนเพดาน token ขั้นสกัดจะเพิ่ม check `reader_complete ✗` (Paddle ไม่มีเพดานจึงเป็น `None`)
  - `confidence`: ความมั่นใจเฉลี่ยที่ engine รายงานเอง มีเฉพาะ Paddle บันทึกเป็น `ocr_confidence`
- **ชื่อในผล:** `<engine>:<โมเดล>` เช่น `openthai:OpenThai2.0-OCR-Markdown` หรือ `typhoon:scb10x/typhoon-ocr1.5-3b` ส่วน Paddle คือ `paddle`
  - ผลที่สกัดก่อน 2026-11-20 ใช้ชื่อ `vlm:<โมเดล>` และ check ชื่อ `vlm_complete`

| engine | ไฟล์ | อ่านอย่างไร | ได้อะไร | หมายเหตุ |
|---|---|---|---|---|
| `openthai` (ค่าตั้งต้น) | `readers/openthai.py` | โมเดลภาพ 0.63B (torch ในเครื่อง) | Markdown | ดู [04-openthai-ocr.md](04-openthai-ocr.md) |
| `typhoon` | `readers/typhoon.py` | โมเดลภาพ 3B ผ่าน Ollama / vLLM / Typhoon API | Markdown | ต้องเปิด Ollama |
| `paddle` | `readers/paddle.py` (+ `readers/lines.py`) | ตรวจกรอบคำแล้วอ่านทีละกรอบ | บรรทัดล้วน + ความมั่นใจรายคำ | ห้ามอยู่ process เดียวกับ torch (cuDNN คนละรุ่น) |
| `oxr` | `readers/oxr.py` | โมเดลภาพ 1.3B (torch ในเครื่อง) | ข้อความ | อ่านไทยไม่ได้ ดู [archive/oxr.md](archive/oxr.md) |

ตัวเรียกโมเดลแบบแชต (`llm_client.py`) ใช้ร่วมกันระหว่าง Typhoon กับ LLM ตัวสกัดของขั้นที่ 5 ส่วน prompt ของ LLM ตัวสกัดอยู่ที่ `extraction/prompts.py`

ไม่มีขั้นตรวจภาษาหรือเลือกภาษา: Typhoon, OpenThai และ OXR อ่านทุกภาษาด้วยโมเดลเดียว (ได้เท่าที่โมเดลเคยฝึก)
ส่วน Paddle ใช้พจนานุกรมตัวอักษรตามที่ตั้ง (`paddle.lang: th` มีไทย ละติน และตัวเลข)

**ภาษาไทยมีเรื่องเฉพาะสองเรื่อง** ที่ต้องแก้หลังอ่านทุกครั้ง
- **ไทยไม่เว้นวรรคระหว่างคำ** แต่ Paddle ตัดคำไทยเป็นชิ้นเล็ก ถ้าต่อด้วยช่องว่างตรง ๆ จะได้ `บ ร ิ ษั ท`
  จึงเว้นวรรคเฉพาะเมื่อภาพมีช่องว่างจริง (ข้อ 3 ของหัวข้อ PaddleOCR)
- **สระอำถูกเขียนเป็นสองตัว** นิคหิต (U+0E4D) + สระอา (U+0E32) ซึ่งเป็นคนละตัวอักษรกับสระอำ (U+0E33)
  และ `unicodedata.normalize` แก้ให้ไม่ได้ ถ้าไม่แก้ คำว่า "จำกัด" ในชื่อบริษัทแทบทุกชื่อจะเทียบไม่ตรง (`normalize_thai` แก้ให้ทุก engine)

### ทำไม Typhoon คืน Markdown ไม่ใช่ JSON

Typhoon OCR เป็น **โมเดล OCR** ไม่ใช่โมเดลที่ตอบตาม schema ได้ ผู้พัฒนาระบุว่าใช้กับ prompt ที่กำหนด
เท่านั้น จึงต้องมีขั้นที่ 5 แปลง Markdown เป็นฟิลด์อีกครั้ง prompt บางแบบในแพ็กเกจที่บอกให้ตอบ JSON
ก็เป็นแค่ซอง `{"natural_text": "<Markdown>"}` ไม่ใช่ฟิลด์ที่สกัดแล้ว (`_strip_wrappers` แกะซองนี้ออก)

โปรเจกต์รุ่นก่อนลองบังคับให้ Typhoon ตอบ JSON ตาม schema เอง ได้ฟิลด์ถูกแค่ 28.6% เทียบกับ 92.9%
เมื่อให้มันอ่านเป็นข้อความแล้วค่อยสกัดด้วยขั้นถัดไป

### ผลเทียบ Tesseract กับ Typhoon (โปรเจกต์รุ่นก่อน)

ชุดทดสอบ 2 ใบ ใช้ตัวสกัด regex ตัวเดียวกัน ต่างกันแค่ผู้อ่าน

| | Tesseract | Typhoon OCR |
|---|---|---|
| ฟิลด์ถูก | 71.4% | 92.9% |
| CER ระดับฟิลด์ | 0.273 | 0.002 |
| เวลาต่อใบ | ~10 วินาที | ~19 วินาที |

## PaddleOCR (`--engine paddle`)

โค้ด: `readers/paddle.py` (`PaddleEngine` คืนคำพร้อมกรอบ, `PaddleReader` แปลงเป็น `ReadResult`) และ `readers/lines.py` (คำ/บรรทัด)
ตั้งค่าใต้ `paddle:` (`lang: th`, `use_angle_cls: false`) รองรับทั้ง API v2 และ v3 ของ PaddleOCR

Tesseract (`tha+eng`) และ EasyOCR (`th, en`) เคยรองรับ ถูกลบออกแล้ว ผลเทียบตอนยังมีอยู่ในหัวข้อ "ผลเทียบสาม engine" ด้านล่าง

### ขั้นย่อย

1. **รัน engine** ได้คำแต่ละคำ พร้อมข้อความ, ความมั่นใจ (0–1) และกรอบ (x0, y0, x1, y1)
2. **จัดกลุ่มเป็นบรรทัด**
   - Paddle คืนกล่องคำลอย ๆ จึงใช้ `group_into_lines`: คำที่ความสูงซ้อนกัน ≥ 50% อยู่บรรทัดเดียวกัน แล้วเรียงซ้ายไปขวา
3. **ต่อคำในบรรทัด** (`OCRLine.text`) โดยเว้นวรรคเฉพาะเมื่อในภาพมีช่องว่างจริง
   - ไทยกับไทย: เว้นวรรคเมื่อช่องว่างกว้างกว่า 50% ของความสูงตัวอักษร
   - อังกฤษหรือตัวเลข: เว้นวรรคเมื่อช่องว่างกว้างกว่า 10%
   - ถ้าไม่ทำขั้นนี้ engine ที่ตัดเป็นคำหรือตัวอักษรย่อย ๆ (เช่น Tesseract) จะได้ `บ ร ิ ษั ท` แทน `บริษัท`
4. **แก้ตัวอักษรไทย** (`normalize_thai`): เปลี่ยน `ํา` (นิคหิต + สระอา) เป็น `ำ`
5. **คืน `ReadResult`**: บรรทัดต่อกันเป็น `text` ความมั่นใจเฉลี่ยทุกคำเป็น `confidence`

### กรอบ (bbox) มาจากไหน

กรอบมาจาก **OCR ไม่ใช่ preprocess** preprocess ทำแค่ภาพ (หมุนตามทิศ ปรับเอียง คงสี) ส่วน Paddle รับภาพนั้นแล้ว
1. โมเดลตรวจจับข้อความ (`PP-OCRv5_server_det`) หากรอบของแต่ละคำ
2. โมเดลอ่านข้อความ (`th_PP-OCRv5_mobile_rec`) อ่านแต่ละกรอบ และให้ความมั่นใจของกรอบนั้น (ความมั่นใจมาจากโมเดลอ่าน ไม่ใช่โมเดลตรวจจับ)
3. โค้ดของโปรเจกต์แปลงรูปหลายเหลี่ยมที่ Paddle คืนเป็นสี่เหลี่ยมแนวตั้งฉาก (`polygon_to_bbox` ใช้ค่าต่ำสุด/สูงสุดของมุม)
4. `group_into_lines` (ของโปรเจกต์ ไม่ใช่ของ Paddle) รวมกรอบคำเป็นบรรทัด

พิกัดทุกกรอบอ้างอิงภาพที่ส่งเข้า ดังนั้น preprocess มีผลทางอ้อม: ภาพเอียงทำให้กรอบหลวม หมุนผิดทิศทำให้ตรวจจับแย่ลง
ตัวอ่านอื่นไม่มีขั้นตรวจจับกรอบและไม่มีความมั่นใจรายคำ
ผลที่ขั้น ocr เก็บมีแค่ข้อความ กรอบไม่ถูกเก็บ ดูกรอบด้วย `scripts/ocr/visualize_bbox.py` ซึ่งให้ Paddle อ่านภาพใหม่เฉพาะไฟล์ที่ระบุ (ผลที่ `04_ocr/<dataset>/paddle/visualize/`)

### ผลเทียบสาม engine บนเครื่องนี้

> วัดตอนที่ยังรองรับสาม engine อ่านทั้งหน้า และใช้ preprocessing แบบเก่า (สอง profile) ปัจจุบันเหลือ Paddle ตัวเดียวกับ preprocessing ชุดเดียว
> เวลาเตรียมภาพในตารางจึงสูงกว่าปัจจุบัน (NL-means ที่ใช้ตอนนั้นปิดแล้ว ดู [02-preprocessing.md](02-preprocessing.md))

รันไปป์ไลน์เต็มแบบอ่านทั้งหน้า (รุ่นเก่า `--mode ocr` ถอดแล้ว) บน RTX 4050 6 GB, CUDA 13 เวลาวัดหลังอุ่นเครื่องแล้ว

| | Tesseract | EasyOCR (GPU) | **PaddleOCR (GPU)** |
|---|---|---|---|
| BITKUB-001 อ่านค่าสำคัญเจอ | 6/6 | 5/6 | **6/6** |
| BITKUB-001 สถานะ | needs_review 0.84 | auto_approved 0.89 | **auto_approved 0.93** |
| BITKUB-001 รายการสินค้า | 2/5 (อ่าน `8.05` เป็น `805`) | 5/5 | **5/5** |
| BITKUB-001 ชื่อผู้ขาย | ไม่มีเว้นวรรค | ขาดการันต์ (`ออนไลน`) | **ถูกทุกตัว** |
| VATGB-001 อ่านค่าสำคัญเจอ | 3/5 | 3/5 | **5/5** |
| เวลา BITKUB / VATGB | **4.5 / 3.7 วิ** | 7.3 / 12.6 วิ | 5.1 / 23.3 วิ |

- **PaddleOCR แม่นที่สุด** โมเดลภาษาไทย `th_PP-OCRv5_mobile_rec` (`lang: th`) อ่านภาษาไทยได้สะอาด
  ตัว OCR เองใช้แค่ราว 0.5 วินาทีบน BITKUB เวลาที่เหลือเป็นขั้นเตรียมภาพ — บน VATGB (2481×3508 px)
  NL-means ใช้ 5.2 วินาที OSD 3.0 วินาที (ทั้งสองขั้นเปลี่ยนแล้ว)
- **EasyOCR ได้ `auto_approved` ทั้งที่ชื่อผู้ขายผิด** (ขาดการันต์) และไม่ได้ยอดก่อนภาษี — กฎตรวจตัวเลข
  ตรวจชื่อไม่ได้ คะแนนจึงผ่าน
- **VATGB ได้ `failed` ทุก engine** ทั้งที่ Paddle อ่านยอดรวม `£20,017.57` ออกมาได้ — ปัญหาอยู่ที่ขั้นที่ 5
  (rules จับบรรทัด `TOTAL` เป็น `subtotal`) ไม่ใช่ OCR
- **ต้องปิด `use_angle_cls` ของ Paddle** ตัวจำแนกทิศรายบรรทัดตัดสินผิดว่าบรรทัดไทยกลับหัวแล้วหมุนกลับ
  อ่านได้ `81-SO-EZOZ` แทน `2023-05-18` (3 จาก 28 บรรทัด) ทิศของทั้งหน้าตรวจแล้วในขั้นที่ 2

## Typhoon OCR (`--engine typhoon`)

โค้ด: `readers/typhoon.py` (ตัวอ่าน + `TYPHOON_OCR_PROMPT`) เรียกโมเดลผ่าน `llm_client.py` ตั้งค่าใต้ `typhoon:`
เข้าใจ layout/ตารางได้ดีกว่า Paddle มาก แต่ไม่มีกรอบตำแหน่งและไม่มีความมั่นใจต่อคำ

### ขั้นย่อย

1. **ย่อภาพ** ให้ด้านยาวไม่เกิน 1800 px (`typhoon.max_image_side`) เพราะโมเดลคิด token ตามขนาดภาพ
2. **Encode** เป็น base64 PNG
3. **ส่ง prompt** (`TYPHOON_OCR_PROMPT`) สั่งให้คืน Markdown, ตารางเป็น `<table>` HTML, ห้ามมีคำอธิบายเพิ่ม
4. **เรียกโมเดล** ผ่าน `llm_client.py` ซึ่งรองรับ 2 provider:

   | provider | endpoint | ใช้กับ |
   |---|---|---|
   | `ollama` (ค่าตั้งต้น) | `http://localhost:11434/api/chat` | Ollama ในเครื่อง ตั้ง `num_ctx` ได้ |
   | `openai` | OpenAI-compatible `/v1` | Typhoon API บน cloud, vLLM |

   ต้องใช้ native API ของ Ollama เพราะ endpoint แบบ OpenAI ตั้ง `num_ctx` ไม่ได้
   ค่าตั้งต้น 4096 token ไม่พอ ภาพ 1 หน้ากินไปราว 3.5k token แล้ว ทำให้โมเดลตอบไม่จบ จึงตั้งไว้ที่ 16384

5. **ทำความสะอาดผลลัพธ์** (`_strip_wrappers`): ลบ ```` ```markdown ```` หรือ `{"natural_text": ...}` ที่บางรุ่นห่อมา
6. **ตรวจว่าตอบจบไหม:** ถ้า `finish_reason = length` ขั้นสกัดเพิ่ม check `reader_complete ✗` เตือนว่าข้อมูลอาจขาด
7. **แปลงเป็นบรรทัด** (`markdown_to_lines`, ขั้นที่ 5): ตาราง 1 แถว = 1 บรรทัด คั่นช่องด้วย ` | ` ลบ tag และตัวหนา

## เปรียบเทียบกับภาพตัวอย่าง

| | Tesseract | Typhoon OCR |
|---|---|---|
| ยอดรายการ | อ่าน `8.05` เป็น `805`, `5.29` เป็น `529` | ถูกทั้ง 5 รายการ |
| ยอดสรุป | ถูกครบ (หลังลบเส้นตาราง) | ถูกครบ |
| โครงตาราง | ไม่มี (เป็นบรรทัดข้อความ) | ได้ `<table>` ครบทุกแถว |
| เวลา | ~4.5 วินาที | ~50 วินาที |

ดูข้อความดิบด้วย `python -m fin_extractor sections <ไฟล์หรือโฟลเดอร์> --engine <engine> --to ocr` (บันทึกที่ `data/04_ocr/<dataset>/<engine>/<วิธี>/<ไฟล์>/` เป็น `.md` ต่อทุกส่วน + `.sections.json` + `.chunks.json` ทุก engine)

ข้อสรุปที่พูดได้อย่างระมัดระวัง
- Typhoon ช่วย **การอ่านข้อความ** (ลายมือ ชื่อ ตาราง) ได้จริง แต่ชั้น **LLM สกัด** แต่งค่าและแปลงปีผิดได้ ผลจึงต้องตรวจทาน ไม่ควรอนุมัติอัตโนมัติ
- ยังไม่มีเฉลย จึงไม่รู้ว่าฝั่งไหนถูกทั้งหมดกี่ค่า ที่ตรวจไปคือค่าที่ขัดกับข้อความดิบหรือ checksum เท่านั้น
- เอกสารที่ไม่ใช่ใบกำกับภาษี (50 ทวิ ใบสำคัญรับเงิน ใบเสร็จศุลกากร) ไม่เข้ากับ schema (ผู้ขาย/ผู้ซื้อ, ยอดก่อน VAT) บทบาทของ `vendor`/`buyer` ใน 50 ทวิจึงกำกวม
