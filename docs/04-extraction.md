# ขั้นที่ 4: สกัด field

แปลงข้อความจากขั้นที่ 3 ให้เป็น `InvoiceData` (ดู `src/fin_extractor/schema.py`) มี 3 ส่วน

## หลักการ

เปลี่ยน "ข้อความ" ให้เป็น "ฟิลด์ที่มีความหมาย" เช่น บรรทัด `รวมทั้งสิ้น 47.56` → `total_amount = 47.56`

| วิธี | ทำงานยังไง | ข้อดี | ข้อเสีย |
|---|---|---|---|
| Rules | หาคำกำกับ (keyword) แล้วดึงค่าด้วย regex | เร็ว อธิบายได้ ไม่ต้องมีโมเดล | เปราะกับผังเอกสารที่ไม่เคยเห็น |
| LLM | ส่งข้อความให้โมเดลภาษาตอบเป็น JSON | ทนกับผังแปลก ๆ | ช้า สลับ field ได้ แต่งตัวเลขได้ |

ไม่ต้องเลือกอย่างใดอย่างหนึ่ง — **รันทั้งคู่ แล้วให้กฎตรวจตัวเลข (ขั้นที่ 5) เป็นกรรมการ** ชุดที่ตัวเลขสอดคล้อง
กันมากกว่าชนะ แล้วเติมช่องที่ขาดจากอีกชุด (4C)

**ลำดับคำกำกับสำคัญ** ต้องตรวจคำที่เจาะจงก่อนคำกว้าง ๆ เสมอ คำกำกับสั้นมักเป็นส่วนหนึ่งของคำยาวที่มี
ความหมายอื่น โปรเจกต์รุ่นก่อนเจอบั๊กจริงแบบนี้หลายตัว

| คำกำกับ | ไปเจออยู่ใน | ผลที่ได้ |
|---|---|---|
| `TOTAL` | `Subtotal` | ยอดรวมทั้งสิ้นกลายเป็นยอดก่อนภาษี |
| `VAT` | `VAT Reg No: GB 933 6364 83` | ยอดภาษีกลายเป็น 933 (มาจากเลขทะเบียน) |
| `ภาษีมูลค่าเพิ่ม` | `มูลค่ารวมภาษีมูลค่าเพิ่ม` | ยอดภาษีกลายเป็นยอดรวม |
| `Invoice No` | — ไม่เจอใน `Invoice Number` | เลขที่เอกสารว่างทุกใบที่เขียนเต็ม (No ≠ Nu) |
| `No.` | หัวตาราง `ลำดับ / No.` | เลขที่เอกสารกลายเป็น `"Description"` |

ภาษาไทยไม่เว้นวรรคระหว่างคำ ปัญหาคำกำกับซ้อนอยู่ในคำอื่นจึงเกิดบ่อยกว่าภาษาอังกฤษ

| ส่วน | ไฟล์ | ทำงานเมื่อ |
|---|---|---|
| 4A Rules | `extraction/rule_extractor.py`, `patterns.py` | ทุกครั้ง |
| 4A+ ชนิดเอกสาร | `doctypes.py`, `extraction/profile_extractor.py` | ทุกครั้ง: จำแนกโปรไฟล์ แล้วสกัด `document_fields`, `remark` และชื่อลูกค้า `buyer.name` จากป้าย (`extraction/core_labels.py`) (ดู [08 หัวข้อ 3.6](08-solution-and-roadmap.md)) |
| 4B LLM | `extraction/llm_extractor.py` | `--mode vlm` (ค่าตั้งต้น) หรือ `--llm on` |
| 4C เลือกผล | `pipeline.py → extract`, `fill_missing` | เมื่อมีทั้ง 4A และ 4B |

## 4A: Rule-based (regex + keyword)

ไล่อ่านทีละบรรทัดจากบนลงล่าง

| Field | วิธีหา |
|---|---|
| `document_type` | keyword: ใบกำกับภาษี → `tax_invoice`, ใบเสร็จ → `receipt`, ใบแจ้งหนี้ → `invoice`, ใบเสนอราคา → `quotation` |
| ผู้ขาย / ผู้ซื้อ | ทุกอย่าง **ก่อน** เจอ "ลูกค้า / Customer / ผู้ซื้อ / Bill to" เป็นของผู้ขาย หลังจากนั้นเป็นของผู้ซื้อ |
| `vendor.name` | บรรทัดแรกที่มี บริษัท, หจก., จำกัด, Co., Ltd, Company |
| `tax_id` | เลข 13 หลัก (รองรับ `0-1055-59117-12-8`) และต้องผ่าน checksum |
| `branch` | เจอ "สำนักงานใหญ่" หรือ "Head Office" |
| `invoice_no` | ค่าหลัง "เลขที่ / Invoice No. / Receipt No." ต้องมีตัวเลขและต้องไม่ใช่เลขภาษี |
| `date` | วันที่ในบรรทัดที่มี "วันที่ / Date" ถ้าไม่เจอใช้วันที่แรกในเอกสาร |
| ยอดเงิน | จำแนกบรรทัด (ลำดับด้านล่าง) แล้วหยิบตัวเลขตัวสุดท้าย ถ้าไม่มีให้ดูบรรทัดถัดไปที่มีแต่ตัวเลข |
| `items` | บรรทัดระหว่างหัวตาราง "รายการ / Description" ถึงบรรทัดสรุปหรือ "หมายเหตุ" |

### ลำดับการจำแนกบรรทัดยอดเงิน

ต้องตรวจคำที่เจาะจงก่อน เช่น "Grand Total (VAT **Excluded**)" มีคำว่า Grand Total อยู่ด้วย ถ้าตรวจ total ก่อนจะผิด

1. `amount_before_vat`: ก่อนรวมภาษี, ไม่รวมภาษี, VAT Excluded, before VAT
2. `total_amount`: รวมภาษี, รวมทั้งสิ้น, ยอดสุทธิ, Grand Total, Net Total, Amount Due
3. `vat_amount`: ภาษีมูลค่าเพิ่ม, VAT (ดึง `7%` มาเป็น `vat_rate = 0.07` ด้วย)
4. `discount`: ส่วนลด, Discount
5. `subtotal`: รวม, รวมเงิน, Subtotal, Total (ป้ายต้องสั้นไม่เกิน 30 ตัวอักษร กันบรรทัดรายการอย่าง "Total THB withdrawal fee on…")

ถ้าเอกสารมีแค่ "รวม / Total" บรรทัดเดียว (ไม่มี VAT และส่วนลด) ระบบใช้ค่านั้นเป็น `total_amount`

### Regex สำคัญ (`patterns.py`)

| ใช้หา | กฎ |
|---|---|
| เลขภาษี | 13 หลัก คั่นด้วยขีดหรือช่องว่างได้ ห้ามมีตัวเลขติดหน้าหลัง |
| ยอดเงิน | ต้องมีทศนิยม 2 ตำแหน่ง หรือมีจุลภาคคั่นหลักพัน จะได้ไม่จับ "7" จาก "VAT 7%" หรือเลขลำดับ |
| วันที่ | `2023-05-18`, `18/05/2566`, `18/05/66`, `18 พฤษภาคม 2566`, `18 พ.ค. 66`, `18 May 2023` |

**การแปลงปี:** ปี ≥ 2400 ถือเป็น พ.ศ. ให้ลบ 543
ปี 2 หลักจะลองทั้ง ค.ศ. (20xx) และ พ.ศ. (25xx − 543) แล้วเลือกปีที่ไม่เกินปีหน้าและใกล้ปัจจุบันที่สุด

### Items
- บรรทัดที่มียอดเงิน = 1 รายการ (ตัดเลขลำดับและตัวเลขออกจากคำอธิบาย)
- บรรทัดที่ไม่มียอดเงิน นำไปต่อเป็นคำอธิบายของรายการถัดไป ถ้าเหลือท้ายสุดจะต่อกับรายการสุดท้าย

## 4B: LLM → JSON

ค่าตั้งต้นใช้ `qwen2.5:3b` ผ่าน Ollama (`llm_extractor.*` ใน config)

1. **ส่ง prompt** (`vlm/prompts.py`):
   - system: กฎการสกัด เช่น ห้ามเดา ไม่พบให้ใส่ null, เลขภาษีต้องติดกัน 13 หลัก, วันที่ใช้ ค.ศ., `vat_rate` เป็นทศนิยม
   - user: JSON Schema ของ `InvoiceData` + ข้อความเอกสาร
2. **บังคับ JSON** (`format: json` สำหรับ Ollama, `response_format` สำหรับ OpenAI)
3. **Normalize** สิ่งที่ LLM มักตอบผิด (`normalize_llm_output`):
   - เลขภาษีมีขีด → ตัดเหลือแต่ตัวเลข
   - วันที่เป็น string รูปแบบไหนก็ได้ → parse ใหม่
   - ยอดเงินเป็น `"1,234.00"` → `1234.0`
   - `vat_rate: 7` → `0.07`
   - `buyer: null` → ตัดทิ้งให้ใช้ค่าว่างตั้งต้น
4. **ตรวจกับ schema** ด้วย pydantic ถ้าไม่ผ่านหรือ LLM ล่ม จะใช้ผลจาก rules แทน

## 4C: เลือกผลและเติม field

LLM ขนาดเล็กมักสลับ field ยอดเงิน ส่วน rules เปราะกับ layout แปลก ๆ จึงใช้ cross-check (ขั้นที่ 5) เป็นตัวตัดสิน

1. รัน validation กับผลทั้งสองชุด
2. คะแนนความสอดคล้อง = จำนวน check ที่ผ่าน − จำนวนที่ไม่ผ่าน
3. เลือกชุดที่คะแนนสูงกว่า (เสมอกันให้ LLM ชนะ)
4. `fill_missing`: field ที่ชุดที่ชนะยังว่างอยู่ ให้เติมจากอีกชุด ไม่เขียนทับค่าที่มีอยู่
