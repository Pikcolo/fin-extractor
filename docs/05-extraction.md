# ขั้นที่ 5: สกัด field

แปลงข้อความจากขั้นที่ 4 ให้เป็น `InvoiceData` (ดู `src/fin_extractor/schema.py`) มี 3 ส่วน

## หลักการ

เปลี่ยน "ข้อความ" ให้เป็น "ฟิลด์ที่มีความหมาย" เช่น บรรทัด `รวมทั้งสิ้น 47.56` → `total_amount = 47.56`

| วิธี | ทำงานยังไง | ข้อดี | ข้อเสีย |
|---|---|---|---|
| Rules | หาคำกำกับ (keyword) แล้วดึงค่าด้วย regex | เร็ว อธิบายได้ ไม่ต้องมีโมเดล | เปราะกับผังเอกสารที่ไม่เคยเห็น |
| LLM | ส่งข้อความให้โมเดลภาษาตอบเป็น JSON | ทนกับผังแปลก ๆ | ช้า สลับ field ได้ แต่งตัวเลขได้ |

ไม่ต้องเลือกอย่างใดอย่างหนึ่ง — **รันทั้งคู่ แล้วให้กฎตรวจตัวเลข (validation 5E) เป็นกรรมการ** ชุดที่ตัวเลขสอดคล้อง
กันมากกว่าชนะ แล้วเติมช่องที่ขาดจากอีกชุด (5C)

**ลำดับคำกำกับสำคัญ** ต้องตรวจคำที่เจาะจงก่อนคำกว้าง ๆ เสมอ คำกำกับสั้นมักเป็นส่วนหนึ่งของคำยาวที่มี
ความหมายอื่น โปรเจกต์รุ่นก่อนเจอบั๊กจริงแบบนี้หลายตัว

| คำกำกับ | ไปเจออยู่ใน | ผลที่ได้ |
|---|---|---|
| `TOTAL` | `Subtotal` | ยอดรวมทั้งสิ้นกลายเป็นยอดก่อนภาษี |
| `VAT` | `VAT Reg No: GB 933 6364 83` | ยอดภาษีกลายเป็น 933 (มาจากเลขทะเบียน) |
| `ภาษีมูลค่าเพิ่ม` | `มูลค่ารวมภาษีมูลค่าเพิ่ม` | ยอดภาษีกลายเป็นยอดรวม |
| `Invoice No` | — ไม่เจอใน `Invoice Number` | เลขที่เอกสารว่างทุกใบที่เขียนเต็ม (No ≠ Nu) |
| `No.` | หัวตาราง `ลำดับ / No.` | เลขที่เอกสารกลายเป็น `"Description"` |

ภาษาไทยไม่เว้นวรรคระหว่างคำ ปัญหาคำกำกับซ้อนอยู่ในคำอื่นจึงเกิดบ่อยกว่าภาษาอังกฤษ

| ส่วน | ไฟล์ | ทำงานเมื่อ |
|---|---|---|
| 5A Rules | `extraction/rule_extractor.py`, `patterns.py` | ทุกครั้ง |
| 5A+ ชนิดเอกสาร | `doctypes.py`, `extraction/profile_extractor.py` | ทุกครั้ง: จำแนกโปรไฟล์ แล้วสกัด `document_fields`, `remark` และชื่อลูกค้า `buyer.name` จากป้าย (`extraction/core_labels.py`) (ดู [06 หัวข้อ 3.6](06-design-and-roadmap.md)) |
| 5B LLM | `extraction/llm_extractor.py` | `extract --llm on` หรือ `auto` / `--llm hybrid` (`--llm off` = rules อย่างเดียว) |
| 5C เลือกผล | `pipeline.py → extract_traced`, `fill_missing` | เมื่อมีทั้ง 5A และ 5B (`--llm auto` หรือ `on`) |

## 5A: Rule-based (regex + keyword)

ไล่อ่านทีละบรรทัดจากบนลงล่าง

| Field | วิธีหา |
|---|---|
| `document_type` | keyword: ใบกำกับภาษี → `tax_invoice`, ใบเสร็จ → `receipt`, ใบแจ้งหนี้ → `invoice`, ใบเสนอราคา → `quotation` |
| ผู้ขาย / ผู้ซื้อ | ทุกอย่าง **ก่อน** เจอ "ลูกค้า / Customer / ผู้ซื้อ / Bill to" เป็นของผู้ขาย หลังจากนั้นเป็นของผู้ซื้อ |
| `vendor.name` | บรรทัดแรกที่มี บริษัท, หจก., จำกัด, Co., Ltd, Company · ใบสำคัญรับเงินอ่านจากป้าย `ข้าพเจ้า` ใน config (`document_types.payment_voucher.core_labels`) |
| `tax_id` | เลข 13 หลัก (รองรับ `0-1055-59117-12-8`) และต้องผ่าน checksum |
| `branch` | เจอ "สำนักงานใหญ่" หรือ "Head Office" |
| `invoice_no` | ป้ายที่เจาะจงที่สุดชนะ (ใบกำกับ/Invoice No. > ใบเสร็จ/Receipt No./เลขที่เอกสาร > เลขที่/No. เปล่า) ต้องมีตัวเลข ไม่ใช่เลขภาษี ไม่ใช่วันที่ ดูหัวข้อ "เลขที่เอกสาร" |
| `date` | วันที่ในบรรทัดที่มี "วันที่ / Date" ถ้าไม่เจอใช้วันที่แรกในเอกสาร |
| ยอดเงิน | จำแนก**ทีละช่อง** ของบรรทัดตาราง (` | `) ตามลำดับด้านล่าง แล้วหยิบค่าของช่องนั้น (ดูหัวข้อถัดไป) |
| `items` | ข้อความมีตาราง HTML: อ่านตารางรายการตามหัวคอลัมน์ (`item_table.py`) · ไม่มีตาราง: บรรทัดระหว่างหัวตาราง "รายการ / Description" ถึงบรรทัดสรุปหรือ "หมายเหตุ" |

### ลำดับการจำแนกบรรทัดยอดเงิน

ต้องตรวจคำที่เจาะจงก่อน เช่น "Grand Total (VAT **Excluded**)" มีคำว่า Grand Total อยู่ด้วย ถ้าตรวจ total ก่อนจะผิด

1. `amount_before_vat`: ก่อนรวมภาษี, ไม่รวมภาษี, VAT Excluded, before VAT
2. `total_amount`: รวมภาษี, รวมทั้งสิ้น, ยอดสุทธิ, Grand Total, Net Total, Amount Due
3. `vat_amount`: ภาษีมูลค่าเพิ่ม, VAT (ดึง `7%` มาเป็น `vat_rate = 0.07` ด้วย)
4. `discount`: ส่วนลด, Discount
5. `subtotal`: รวม, รวมเงิน, Subtotal, Total (ป้ายนับจากคำที่เจอถึงท้ายช่องต้องไม่เกิน 30 ตัวอักษร กันบรรทัดรายการอย่าง "Total THB withdrawal fee on…")

ป้ายที่เพิ่ม (2026-11-24) มีตัวอย่างจริงทุกตัว: `มูลค่าสินค้า` / `ก่อนคิดภาษี` → ก่อน VAT (1310, 1312) · `รวมเงินทั้งสิ้น` `ยอดเงินสุทธิ` → ยอดรวม (1316, 1317–1319) · `V.A.T.` → VAT (1317–1319)
ป้าย `ยกเว้นภาษี` / `Non-Taxable` (มูลค่าสินค้าที่ยกเว้นภาษี 1310, Non-Taxable Charges 1313) ไม่จัดเป็นช่องใด — เดิมถูกจับเป็น VAT

ถ้าเอกสารมีแค่ "รวม / Total" บรรทัดเดียว (ไม่มี VAT และส่วนลด) ระบบใช้ค่านั้นเป็น `total_amount`

### หยิบค่าให้ป้าย (ทีละช่อง)

เดิมจำแนกทั้งบรรทัดด้วยป้ายแรกที่เจอแล้วหยิบตัวเลขตัวท้ายของบรรทัด แถวตารางที่มีหลายป้าย/หลายค่าจึงได้ค่าผิดช่อง ตอนนี้:

- ค่าในช่องเดียวกับป้าย (ตัวท้าย) → ไม่มีก็ใช้ค่า**เดียว**ในช่องถัดไปก่อนถึงช่องป้ายถัดไป → ไม่มีก็บรรทัดถัดไปที่มีแต่ตัวเลข
- ป้ายหลายตัวในช่องเดียว + ตัวเลขเท่าจำนวนป้ายในช่อง/บรรทัดถัดไป → จับคู่ตามลำดับ (1312: `รวมเป็นเงิน จำนวนภาษีมูลค่าเพิ่ม 7% รวมมูลค่าสินค้า` กับ `3,949.00 258.35 3,690.65`)
- ป้ายเดียวตามด้วยหลายค่าที่จับคู่ไม่ได้ → ไม่ใส่ (50 ทวิ `รวมเงินที่จ่ายและภาษีที่หักนำส่ง | 106,250.00 | 3,187.50`)
- ช่องบาท|สตางค์ (`103,062 | 50` 1320) รวมเป็น 103,062.50 เฉพาะค่าของป้าย · `7,500:00` (OCR อ่านจุดเป็น `:`) อ่านเป็น 7,500.00 เฉพาะเลขที่มีจุลภาคหลักพัน

ผลวัด (OpenThai regions 14 ใบที่ไม่ใช่ 50 ทวิ เทียบค่าที่อ่านจากภาพสแกนด้วยตา ไม่ OCR ใหม่): ช่องยอดเงินถูก 18 → **27** ผิด 3 → **0** ขาด 16 → **10** ใส่เกิน 1 → **0**
ที่ยังขาด: 1306 (3) และ 1310 (4) OCR ไม่ได้ค่ามา (กล่องยอดหาย / แถวสลับ) · 1312 ยอดรวม และ 1313/1314 ยอดก่อน VAT ไม่มีป้ายที่ชี้ชัด ต้องใช้เลขคณิต (ก่อน VAT + VAT = ยอดรวม) ซึ่งยังไม่ทำ เพราะต้องบันทึกว่าค่ามาจากการคำนวณ ไม่ให้ check สูตรเดียวกันยืนยันตัวเอง

### Items

**ข้อความที่มีตาราง HTML (OpenThai, Typhoon) — อ่านตามหัวคอลัมน์ (`extraction/item_table.py`, 2026-11-25)**

เดิมแยกทีละบรรทัดโดยไม่รู้ว่าตัวเลขอยู่คอลัมน์ไหน: จำนวน 1.00 กลายเป็นยอด หน่วยกับราคาแตกเป็นรายการใหม่ (1310 ได้ 21 รายการจาก 7) แถวยอดรวมท้ายตารางเป็นรายการ (1308, 1313) และไม่เคยได้จำนวนเลย

1. หาแถวหัวตาราง: มีคอลัมน์คำอธิบาย + คอลัมน์ยอดเงิน และไม่มีตัวเลขยอดเงิน (ไม่ต้องเป็นแถวแรก)
2. บทบาทคอลัมน์จากคำในหัว ตัวที่เจาะจงก่อน: `จำนวนเงิน/Amount/Net Charges/รวม` → ยอด · `ราคา/Price/หน่วยละ` → ราคาต่อหน่วย · `หน่วย/Unit` → หน่วยนับ (ไม่ใช้) · `จำนวน/Qty` → จำนวน · `รหัส/Code/Article Number` → รหัส · `รายการ/Description/ชื่อสินค้า` → คำอธิบาย
   หัวที่ colspan หลายช่อง (`จำนวนเงิน (บาท)` = บาท|สตางค์ 1320) ขยายตามจำนวนช่อง ช่องที่สองเป็นสตางค์
3. แถวหลังหัว = รายการ จนเจอแถวสรุป (ช่องที่เป็นป้ายยอดเงินสั้น ๆ ชุดเดียวกับตัวแยกยอด หรือจำนวนเงินตัวอักษร `…บาทถ้วน`) แถวที่ไม่มียอดไม่ใช่รายการ
4. ตารางที่ถูกตัดหลายท่อนมีหัวซ้ำทุกท่อน (regions repeat-header) จึงอ่านทีละตารางได้
5. ช่องเดียวมีหลายค่า (1309: จำนวน `1 2` ยอด `115.00 3,860.00`) แยกเป็นหลายรายการเมื่อทุกคอลัมน์ตัวเลขมีจำนวนค่าเท่ากัน คำอธิบายแยกไม่ได้จึงใช้ทั้งช่องกับทุกรายการ
6. มีตารางแต่ไม่มีตารางรายการ = ไม่มีรายการ (ไม่ถอยไปแยกทีละบรรทัด ซึ่งให้รายการขยะใน 50 ทวิ/ใบศุลกากร/1313)

ผลวัด (OpenThai regions 18 ใบ เทียบรายการที่อ่านจากภาพสแกน: จำนวน ราคาต่อหน่วย ยอด และคำในคำอธิบาย): ใบที่ถูกครบ 1 → **18** · แถวที่ตรง 2/22 → **22/22** · แถวเกิน 50 → **0** · จำนวนถูก 0/16 → **16/16**
ผัง sections เดิม (`openthai/luma`) ได้แค่ 5/22 เพราะผังนั้นตัดตารางเป็นแถวโดยไม่ต่อหัว ท่อนหลังไม่มีหัวให้อ่าน (ยังดีกว่าแบบทีละบรรทัด 4/22 แถวเกิน 51 → 1)

**ข้อความไม่มีตาราง (OpenThai Text, Paddle)** — แบบเดิม
- บรรทัดที่มียอดเงิน = 1 รายการ (ตัดเลขลำดับและตัวเลขออกจากคำอธิบาย)
- บรรทัดที่ไม่มียอดเงิน นำไปต่อเป็นคำอธิบายของรายการถัดไป ถ้าเหลือท้ายสุดจะต่อกับรายการสุดท้าย

### เลขที่เอกสาร

- ป้ายเรียงความเจาะจง ตัวที่เจาะจงกว่าชนะไม่ว่าอยู่ตรงไหน: เลขที่ใบกำกับ/Invoice No. > เลขที่ใบเสร็จ/Receipt No./เลขที่เอกสาร > "เลขที่" / "No." เปล่า
  "No." เปล่านับเฉพาะต้นช่อง ("Account No." 1313, "Hawb No." 1316 ไม่ใช่เลขที่เอกสาร)
- อ่านค่าได้สามแบบ: หลังป้าย · ก่อนป้ายอังกฤษในช่องเดียวกัน (`ใบวางบิล : IN-691005003 Invoice No` 1306) · ใต้หัวตาราง (`เลขที่ | ออกเมื่อ` → แถวถัดไป 1312)
- ไม่รับ: ค่าหลัง "เลขที่" ที่เป็นที่อยู่ (`เลขที่ 49/12 ซอย 6 ถนน …` 1308/1309) · ค่าที่เป็นวันที่ (1322 OCR ใส่วันที่ไว้บรรทัดเลขที่) · เลขภาษี

ผลวัด (14 ใบที่มีเลขที่บนเอกสาร): ถูก 1 → **5** ผิด 6 → **1** (1320 ป้ายถูกแต่ OCR อ่านลายมือ `imps-` เป็น `https-`) ที่เหลือ 6 ใบ OCR ไม่ได้ค่ามา: 1308/1309 แถว Invoice No. หาย · 1317–1319 กล่องขวาหายทั้งกล่อง · 1322 ลายมือ

## 5B: LLM → JSON

ค่าตั้งต้นใช้ `qwen2.5:3b` ผ่าน Ollama (`llm_extractor.*` ใน config)

1. **ส่ง prompt** (`extraction/prompts.py`):
   - system: กฎการสกัด เช่น ห้ามเดา ไม่พบให้ใส่ null, เลขภาษีต้องติดกัน 13 หลัก, วันที่ใช้ ค.ศ., `vat_rate` เป็นทศนิยม
   - user: JSON Schema ของ `InvoiceData` + ข้อความเอกสาร
2. **บังคับ JSON** (`format: json` สำหรับ Ollama, `response_format` สำหรับ OpenAI)
3. **Normalize** สิ่งที่ LLM มักตอบผิด (`normalize_llm_output`):
   - เลขภาษีมีขีด → ตัดเหลือแต่ตัวเลข
   - วันที่เป็น string รูปแบบไหนก็ได้ → parse ใหม่
   - ยอดเงินเป็น `"1,234.00"` → `1234.0`
   - `vat_rate: 7` → `0.07`
   - `buyer: null` → ตัดทิ้งให้ใช้ค่าว่างตั้งต้น
4. **ตรวจกับ schema** ด้วย pydantic ถ้าไม่ผ่านหรือ LLM ล่ม จะใช้ผลจาก rules แทน

## 5C: เลือกผลและเติม field

LLM ขนาดเล็กมักสลับ field ยอดเงิน ส่วน rules เปราะกับ layout แปลก ๆ จึงใช้ cross-check (validation 5E) เป็นตัวตัดสิน

1. รัน validation กับผลทั้งสองชุด
2. คะแนนความสอดคล้อง = จำนวน check ที่ผ่าน − จำนวนที่ไม่ผ่าน
3. เลือกชุดที่คะแนนสูงกว่า (เสมอกันให้ LLM ชนะ)
4. `fill_missing`: field ที่ชุดที่ชนะยังว่างอยู่ ให้เติมจากอีกชุด ไม่เขียนทับค่าที่มีอยู่

## remark: ข้อมูลสำคัญที่ไม่มีช่อง ไม่ถูกทิ้ง

`data.remark[]` (`ExtraField`) เก็บสิ่งที่เอกสารพิมพ์ไว้แต่ไม่มีช่องใน schema ของชนิดเอกสารนั้น แต่ละรายการมี
- `kind = "pair"`: บรรทัดรูป `ป้าย: ค่า` ที่ไม่มีช่องรองรับ (`extract_remark`)
- `kind = "unmapped"`: **บรรทัดที่มียอดเงิน / วันที่ / เลขภาษี (checksum ผ่าน) แต่ไม่มีค่าใดเลยตรงกับช่องที่สกัดไว้** (`extract_unmapped`) ป้ายคือ `(ไม่มีช่องรองรับ)` ค่าคือทั้งบรรทัด ไม่ตัด (ยาวสุดที่เจอ 783 ตัวอักษร จากแถวตารางที่ OCR ต่อเป็นบรรทัดเดียว ตัดแล้วอาจทำให้ยอดที่ทำให้บรรทัดนั้นถูกเก็บหายไป) ใช้ตัวจับชุดเดียวกับตัวสกัด ไม่มีเกณฑ์ที่ตั้งเอง บรรทัดที่ไม่มีสัญญาณเหล่านี้ (เช่น ชื่อบริษัทที่มีช่องอยู่แล้ว หัวตาราง) ไม่ถูกเก็บ เลข 13 หลักที่ checksum ไม่ผ่าน (รหัสสินค้า) ไม่นับ
- `source_chunk`: รหัส section (`sNN`) ที่บรรทัดนั้นมา อ่านจากคอมเมนต์ `<!-- sNN kind -->` ใน `.md` ของขั้น OCR รายส่วน (`lines_with_chunks`) เปิด `04_ocr/.../<ไฟล์>_p1.chunks.json` ดูภาพ section นั้นได้ `None` = อ่านทั้งหน้า (ไม่มีคอมเมนต์)

วัดบน 18 ใบ (OpenThai luma): `unmapped` ได้ 19 บรรทัด ส่วนใหญ่เป็นยอดชำระ/ยอดรวมที่ไม่มีช่องของชนิดนั้น (1306 "ยอดชำระ Total", 1308/1309 "NET TOTAL WORDS"), เลขภาษีของผู้ถูกหักใน 50 ทวิ (1307, 1323) และวันที่ในใบขนส่ง (1313, 1314) **ไม่ได้เปลี่ยนสถานะ ฟิลด์ที่ขาด หรือ check ของไฟล์ใดเลย** (เทียบ 18 ไฟล์ × luma/flat/bin กับก่อนเพิ่ม) ข้อจำกัด: บรรทัดรายการสินค้าที่ OCR ต่อเป็นบรรทัดเดียวก็ถูกเก็บได้ (1319)

`ExtractionResult.rejected[]` (โหมด `--llm hybrid`): ค่าที่ LLM เสนอแต่ด่านปัดตก พร้อมเหตุผล (เดิมแค่พิมพ์ขึ้นหน้าจอ) ไว้ debug ว่าทำไมช่องนั้นว่าง

## 5D: แบบ hybrid (ทดลอง, `--llm hybrid`)

ทางเลือกแทน 5C: rules กับ LLM ทำงานต่อกันในขั้นสกัดเดียว ไม่เลือกผู้ชนะทั้งชุด (โค้ด `extraction/hybrid.py`, ผลลง `data/05_extract/<dataset>/<engine>/<วิธี>/hybrid/`)

1. rules สกัดก่อน
2. หา "ช่องที่ยังไม่เสร็จ" = ฟิลด์ที่ชนิดเอกสารต้องมีแต่ว่าง + ฟิลด์ที่อยู่ใน check ที่ไม่ผ่าน (ไม่มีเกณฑ์ตัวเลขที่ตั้งเอง) ถ้าไม่มีก็ไม่เรียก LLM
3. ถาม LLM เฉพาะ property ที่มีช่องค้าง และระบุชื่อช่องที่ขาดเป็นคำถามตรง ๆ
4. ค่าจาก LLM ต้องผ่านด่านก่อนรับ: อยู่ในข้อความ (กฎเดียวกับ `grounded` ใน evidence), เลขภาษีผ่าน checksum, ยอดเงิน/รายการแล้ว check รวมไม่แย่ลง ถ้าไม่ผ่านจะเป็นค่าว่าง ไม่เดา
5. ช่องที่ rules ได้แล้วและไม่ติดใจ LLM ไม่แตะ และ remark ใช้ของ rules เท่านั้น

ตัวเลขนี้เป็นสถานะจาก check ภายในและการค้นหาในข้อความ **ไม่ใช่ความถูกต้อง** (ไม่มี ground truth) ข้อสรุปที่รองรับด้วยข้อมูล:

- **ได้:** ค่าที่ไม่ปรากฏในข้อความหายไปหมด (0 เทียบ 62/28) และ conflict ลดลงมาก ตัวอย่างที่ด่านทำงานจริง: winner "กู้" `total_amount` ของ OpenThai 001309 ได้ 3995.80 ซึ่งไม่อยู่ในข้อความเลย (คำนวณหรือแต่ง) แล้วใบนั้นถูก `auto_approved` ด้วยค่านี้ hybrid ปัดค่านี้ทิ้ง
- **เสีย:** กู้ฟิลด์ที่ขาดได้น้อยกว่า winner บน OpenThai (ขาด 17 เทียบ 8, `failed` ยัง 4 ใบ) ค่าที่ winner ได้สำหรับ 50 ทวิ 001307 (2,000.00 / 60.00) อยู่ในข้อความจริง แต่ hybrid ไม่ได้ค่านี้เพราะ LLM `qwen2.5:3b` ตอบ `null` เมื่อถูกถามเฉพาะช่อง (ลองแล้วทั้งมีและไม่มีค่าที่ rules ได้แล้วเป็นบริบท ผลเหมือนกัน) ส่วนตอนถามทั้ง schema ตอบได้
- **ข้อสังเกตที่ต้องระวัง:** ค่าที่ rules ใส่ผิดแต่ไม่มี check จับ (001307: `discount = 2000.00` ทั้งที่เป็นยอดจ่าย) ถูกส่งให้ LLM เป็นบริบท "ที่ตรวจแล้ว" ด่านนี้จับค่าผิดของ rules เองไม่ได้
- **`auto_approved` ของ hybrid เพิ่ม (Typhoon 0 → 4) แต่ไม่ถือเป็นข้อดี:** เกณฑ์เดิมคือฟิลด์ครบ + ไม่มี check ตก + มี check ผ่านอย่างน้อยหนึ่งข้อ ซึ่งเลขภาษีผ่าน checksum ก็นับ เช่น Typhoon 001319 `subtotal` 7,500.00 / `total` 8,026.00 ไม่มี VAT ให้เทียบ ผ่านได้ด้วย check เลขภาษีอย่างเดียว ควรตรวจมือก่อนเชื่อใบเหล่านี้ และทบทวนเกณฑ์ `auto_approved` แยกต่างหาก
- ผลของ LLM เปลี่ยนตาม prompt: รอบแรก (ไม่ระบุชื่อช่องที่ขาด) ได้ OpenThai ขาด 12 / auto 3 รอบนี้ขาด 17 / auto 1 จึงเทียบรอบต่อรอบด้วยตัวเลขเล็ก ๆ ไม่ได้

**ทิศทางถัดไปที่มีหลักฐานรองรับ:** ใช้ผลของการถามทั้ง schema (แบบ winner) เป็นแหล่งค่าที่เสนอ แล้วรับรายฟิลด์ผ่านด่านเดียวกันนี้ (ยังไม่ได้ทำ)
